Building, linking & debugging

Reading the code is one thing; making it build and telling a crash log apart from a feature is the other. This page is the bridge: how source becomes a binary in this project, what the linker is really doing, and how the emulator tells you what broke.

Read

For a web engineer the mental model is: TypeScript + bundler + linter + test runner, transplanted to a compiled language. The pieces line up almost one-to-one, and the differences are the interesting parts.

The toolchain at a glance

The project deliberately restricts itself to one compiler family, one build generator, and one linker:

PieceChoiceWhy
LanguageC++20set(CMAKE_CXX_STANDARD 20) in the root CMakeLists.txt — the consteval/requires/if constexpr from topic C1 need it.
CompilerClang only (MSVC rejected at configure time)No other compiler has __attribute__((sysv_abi)), which every HLE function needs. CMake fails with "only Clang and GCC are supported" if you try cl.exe.
Build generatorNinjaFast, parallel, single command. Configure with -G Ninja.
Linkerlld (or lld-link on Windows)LLVM's linker; chosen because the compiler is LLVM's. Emits the map file that turns crash addresses into symbols.
ShadersglslangValidatorFound at configure time (find_program(... REQUIRED)) and run during the build to turn GLSL into embedded SPIR-V.

The very first line of output when you run the emulator is the build string, and it is there to tell you exactly which of these you are running:

src/main.cpp — GetBuildString
fmt::format("{}, {}, ver = {}, git = {}, date = {}",
            type.c_str(), compiler.c_str(),   // e.g. "Debug, clang-lld-64"
            KYTY_VERSION, KYTY_GIT_VERSION, date.ToString().c_str());

When you see a bug report, that first line is the reproduction conditions in one line.

Configure and build — the three commands

The whole build is three commands, and understanding what each does is the point of this section:

first build, from the repository root
git submodule update --init --recursive

cmake -S . -B _Build/windows -G Ninja ^
  -DCMAKE_BUILD_TYPE=Release ^
  -DCMAKE_C_COMPILER=clang-cl -DCMAKE_CXX_COMPILER=clang-cl ^
  -DCMAKE_PREFIX_PATH="C:/Qt/6.x.x/msvc2022_64"

cmake --build _Build/windows --target launcher
cmake --install _Build/windows --prefix _Build/windows/install

Step 1 — dependencies. Everything the emulator links against lives in 3rdparty/ as git submodules: SDL2 (windows/input), FFmpeg (audio/video decode), SPIRV-Tools, VulkanMemoryAllocator, fmt, gtest, magic_enum, imgui, Zydis (x86 disassembler), xbyak (x86 assembler), LibAtrac9. This is the equivalent of npm install — except the versions are pinned as commits, like a lockfile.

Step 2 — configure. CMake's configure pass does the detection work: verifies 64-bit (if(NOT CMAKE_SIZEOF_VOID_P EQUAL 8) message(FATAL_ERROR ...)), detects endianness (test_big_endian), checks the compiler is Clang, finds glslangValidator, and generates two headers — cmake_config.h (compiler/linker/platform macros) and kytyGitVersion.h (the git hash from generate_version.cmake). Nothing compiles yet.

Step 3 — build. Compile and link. Everything after this is the rest of the page.

What actually compiles

The source list is collected with file(GLOB ... CONFIGURE_DEPENDS) — a huge recursive glob over src/libs, src/graphics (through guest_gpu, host_gpu/renderer/cache|image|pipeline, shader/recompiler/cfg|decompiler|emitter|ir, presentation), src/kernel, src/loader, plus main.cpp. The glob is why adding a new .cpp in those directories needs a CMake re-run to be picked up.

Then the genuinely unusual part: the GPU's compute shaders are compiled during the build. A custom CMake command runs glslangValidator on each gpu_tiler_*.comp, and embed_spirv.cmake turns the resulting .spv file into a C header containing the bytes as an array:

CMakeLists.txt — one embedded shader
COMMAND "${KYTY_GLSLANG_VALIDATOR}" -V --target-env vulkan1.0 -Os
        "-I${gpu_tiler_shader_dir}" -o "${shader_spv}" "${shader_source}"
COMMAND ${CMAKE_COMMAND} -DINPUT=${shader_spv} -DOUTPUT=${shader_header}
        -DSYMBOL=${shader_symbol} -P "${KYTY_SOURCE_DIR}/embed_spirv.cmake"

So the emulator's own GPU shaders ride inside the binary as byte arrays — no asset loading at runtime, no missing-file bugs. Same trick as the JIT machine code from topic C2: code becomes data at build time.

Linking — what your bundler wishes it was

Each .cpp is compiled into its own translation unit, producing an object file. The compiler sees exactly one file plus its includes. When you call a function declared in a header, the compiler just records "there will be a symbol called X somewhere". It is the linker that joins every object file (and the 3rdparty libraries) and resolves those references — the analogue of your bundler resolving imports, but with the whole program laid out into one binary.

Three facts make linker errors readable:

  • Internal linkage — a function or global marked static at file scope (like every HLE implementation) exists only inside its own translation unit. The linker never sees it, which is why two files can both have a static helper with the same name without colliding.
  • The One Definition Rule — a non-static function defined in a header is defined in every translation unit that includes it, so it must be inline. That is why you see inline on the small helpers in headers like vaContext.h.
  • Unresolved symbols — "unresolved external symbol" / "undefined reference" means the declaration had no definition in any linked object. Almost always a missing source file in a CMake target, or a function you added a call to but never wrote.

Two linker details worth knowing because they exist here. On Windows, the binary is linked with /lldmap: (Linux: -Wl,-Map=) which writes a map file — the full address→symbol table of the final binary. That, plus a PDB, is how a raw address from a crash becomes a function name. And CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS ON tells the linker to export everything from the shared parts without hand-written __declspec(dllexport) annotations.

No exceptions, no RTTI — and what that means

The compiler flags in src/utils.cmake set the tone for the whole codebase:

src/utils.cmake — the clang flags
set(KYTY_CPP_FLAGS "${KYTY_CPP_FLAGS}
    -fno-rtti -fno-exceptions
    -fno-strict-aliasing -fno-omit-frame-pointer -Wall
    -fcolor-diagnostics ...")

Two consequences ripple through everything:

  • No try/catch, no dynamic_cast, no typeid. That is not an accident or a style choice — they would not compile. The project's error strategy (covered next) is explicit EXITs and return codes instead. Exceptions are also disabled because guest code crashes must not be recoverable as if they were host errors.
  • -fno-omit-frame-pointer is the reason the crash logs can walk the stack. Every function keeps its frame pointer, so the debugger (and the emulator's own crash handler) can walk up the call stack without debug info.

How the project fails: EXIT and EXIT_IF

There is no exception to throw, so a fatal condition is spelled with a macro that prints a report and kills the process:

src/common/assert.h — abridged
#define EXIT(...)                                                     \
    do {                                                              \
        ((void)(Common::DbgExitHandler(__FILE__, __LINE__,            \
                ::fmt::sprintf(__VA_ARGS__)) &&                       \
               (EXIT_HALT(), 1)));                                    \
    } while (0)

#define EXIT_IF(x) ((void)((x) && Common::DbgExitIfHandler(#x, __FILE__, __LINE__) != 0 \
                           && (EXIT_HALT(), 1) != 0))

DbgExitHandler builds a fatal report — a --- Build --- line, a host stack trace, and the file:line plus message — writes it through the logging system, triggers Subsystems::EmergencyShutdownActive(), and exits with status 321. A few notes:

  • __FILE__ and __LINE__ are compiler-provided strings — the "where" is automatic. That is also why you see __func__ in PRINT_NAME: the same family of built-ins.
  • EXIT_IF(x) compiles to nothing when built with KYTY_FINAL — a release-with-asserts-off switch, exactly like NDEBUG disabling assert.
  • The do { } while(0) wrapper is the canonical way to make a multi-statement macro safe to use in an if body without braces — one of the reasons macros survive in this codebase.

Reading a crash log

Guest code runs natively, so when the game hits a bad pointer the host OS delivers an exception to the emulator process, and KytyExceptionHandler (in runtimeLinker.cpp) writes a forensic dump before dying. Read it in order, and every block has a job:

the shape of the dump — annotated
kyty_exception_handler: 0x0000000009006436_4e   the host address that faulted
exception module: D:\Games\Example\eboot.bin   which module owns it
code-32: 48 8b 5c 24 50 48 8b ...              the 32 bytes around the fault, so you can
                                               decode the instruction that died
exception: type=AccessViolation, av_type=Write, av_addr=0000000900_64364e,
           native_code=00000000_c0000005     read / write / execute, and the address
regs: rax=... rbx=... rcx=... rdx=...        every register, because the instruction's
regs: rsi=... rdi=... rbp=... rsp=...        operands live there
stack: [00]=... [01]=...                     the first words of the stack
guest rax[0]: addr=..., off=..., module=...  each register treated as a pointer into a
                                             loaded game module, dumped and tagged
Stack trace [thread = 1]:                    the guest's call stack, each frame with its
[0] 00000009006a_1234, off=00000000000012ab, eboot.bin   module offset — the cause, not the symptom

Three habits make this fast to read:

  • The faulting address is usually a symptom. av_addr is where the write went — often a null, a stale pointer, or a mis-read argument. The cause is in the Stack trace, which names the module and offset of every caller. Translate the module+offset with the map file or a disassembler.
  • The code-32 bytes are the instruction. If you can decode them (objdump, a hex-to-instruction tool, Zydis is in-tree), you know exactly which machine instruction died and which register it needed.
  • The emulator tells you when it is its own fault. A write to the special g_invalid_memory address prints (Unpatched object) — a known bug class in the patching layer, not a game bug. And on Windows, the --redzone flag (from topic C2) is how you opt into protecting the guest's System V red zone.

This is the same output the bug-report template asks you to attach. When a game misbehaves, the log — not the screen — is the evidence.

The tests

Tests are gtest-based and registered with CTest. Fifteen executables, each deliberately small — the interesting bit is that each compiles only the sources it needs:

src/CMakeLists.txt — one focused test
add_executable(bit_array_tests EXCLUDE_FROM_ALL
    "${KYTY_TESTS_DIR}/BitArrayTests.cpp"
)
target_include_directories(bit_array_tests PRIVATE ${inc_headers})

add_executable(memory_tracker_tests EXCLUDE_FROM_ALL
    "${KYTY_TESTS_DIR}/MemoryTrackerTests.cpp"
    "${KYTY_SOURCE_DIR}/graphics/host_gpu/pageManager.cpp"
    "${KYTY_SOURCE_DIR}/graphics/host_gpu/memoryTracker.cpp"
)

EXCLUDE_FROM_ALL means nothing builds until you ask — you build them all with one target, then run everything with ctest:

build and run the whole suite
cmake --build _Build/windows --target kyty_tests
ctest --test-dir _Build/windows --output-on-failure

Some tests are one binary with many modes — shader_recompiler_compute_tests takes --scheduler-only, --gpu-tiler-only, --texture-cache-image-views, and friends so one heavy build covers many subsystems. When you add a change (like an HLE function), the README asks for a test "where practical"; these focused executables are the pattern to copy.

The one mental shift

In JS nothing checks whether the function you called actually exists until runtime. Here the linker checks it before the program ever runs, and static_assert checks facts about the types themselves during compilation. The price is that errors appear earlier and louder; the payoff is that "it builds" genuinely means something.

Try

The fastest way to learn a toolchain is to break it on purpose, once.

A ten-minute lab

Take any file in src/libs/ and temporarily add EXIT_IF(true) to a function the game calls. Rebuild, run, and read the fatal report that comes out: the --- Build --- label, the host stack trace, and the file:line of your edit. Then add LOGF("x %llu\n", (unsigned long long)1) somewhere reachable and watch it appear in _kyty.txt under --printf-direction File. Restore, rebuild, and you have done the whole debug loop end to end.

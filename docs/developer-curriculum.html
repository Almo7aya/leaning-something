Read, trace, prove
Scope, not a promise of completeness

This is a route from reading the emulator to making a defensible change. It is pinned to d2413fc2 (7 October 2026), not a guarantee about future main. The traces follow selected real source paths; the labs deliberately introduce caller mistakes in isolated fixtures. They do not demonstrate that a game works, and they do not claim upstream has these bugs.

Before you start

Before this contributor track, build a small C++20 executable, read pointers and half-open ranges, distinguish integers from addresses, and explain ownership and synchronization. If any are new, follow Start here through the beginner lessons, foundations and both source traces; read C4 before threaded changes. The project practice checklist is an optional companion for readers who already meet these prerequisites. Use the gates below as evidence of developer readiness.

Keep two roots distinct: this learning repository, and the emulator checkout at KytyPS5/. Run the native labs from the learning root. Run emulator build commands from the emulator root. The committed site can be served directly. Authors regenerate shared excerpts and navigation with the documentation script. Beginner labs need only CMake and a C++20 toolchain; these developer labs also use the emulator source checkout.

git -C KytyPS5 rev-parse HEAD
git -C KytyPS5 status --short
git status --short

Record the full source SHA, compiler, OS and test command. If your checkout differs, compare the named functions before trusting the trace. Do not reset an existing worktree just to match a lesson.

The core route has already introduced the boot and draw traces. Review that evidence here, then follow diagnostics, reading a run, the worked diagnosis, the debugging labs and your first change. The gates below assess evidence; they do not define a competing chapter order.

Capstone: make one claim you can defend

Choose a small behavior whose contract you can establish. A regression test for a working subsystem is a valid contribution; a guessed HLE success stub is not automatically one. For memory work, start from a boundary case. For graphics work, narrow a mismatch to a specific draw, shader or binding before changing the compiler.

  1. Write the expected behavior, its source of evidence, and a falsifiable failure condition.
  2. Preserve the pre-change failure: exact input, source revision, output and exit status. Remove unrelated variables.
  3. Make the smallest fix; test ordinary, boundary and error behavior. Explain why the fix belongs at this layer.
  4. Inspect ownership and concurrency across callers. A correct return value can still conceal stale memory or early destruction.
  5. Build the affected targets. Run focused tests, then broader checks in proportion to the risk. Keep game verification separate and use your own lawful content if needed.
  6. Review the diff for accidental formatting, probes and unsupported claims. Follow upstream's contribution policy before submitting.

Keep the curriculum current

On an upstream update, compare the old and new source revisions, re-walk the functions named by D2/D3, rebuild the labs and re-run the documentation checks. Edit the owning topic paragraphs and docs/content/learning.json, regenerate shared copies and navigation with scripts/build-docs.cjs --write, then regenerate the search index. Review unique long-form explanations separately. A source-symbol check detects a renamed function, not a semantic change; manual review is still required.

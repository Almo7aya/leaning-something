Assembly, the ABI & machine code

Guest code runs natively, so the boundaries between host and guest are crossed in raw assembly. This page teaches you to read the small number of hand-written asm blocks in the tree — and the odder part: structs whose bytes are x86 instructions, generated at runtime.

Read

C++ cannot express "swap the stack pointer to an address in guest memory and jump". When the emulator needs that kind of control it writes assembly by hand. There are exactly four such boundaries in the tree, and together they cover every asm block you will ever see here.

Where assembly appears

Four places need exact register and stack control that no compiler construct provides:

BoundaryWhat has to happenWhere
Guest thread entryJump onto a freshly allocated guest stack — swap rsp/rbp to guest memory, call the entry point, swap backruntimeLinker.cpp
Context save / restoreDump the CPU state into a struct, and later restore it — a hand-rolled fiber switchlibKernel.cpp — FiberSaveContext / FiberRestoreContext
Return-address repairAn unrecoverable stub returns by adjusting the stack and ret — no C++ body at allruntimeLinker.cpp — RelocateHandlerReturnStub
Generated thunksImport stubs, PLT trampolines and TLS guards emitted as bytes at runtimeloader/jit.h

x86-64 in ten lines

Everything below needs only a handful of registers. A fuller register tour is in topic 03; the abbreviated list:

rax rbx rcx rdx        general purpose; rax also carries the return value
rsi rdi                argument registers (and the "S"/"D" asm constraints)
rbp rsp                frame pointer / stack pointer — the stack moves toward lower addresses
r8 r9 r10 r11 r12 r13 r14 r15
rip                    instruction pointer — you jump with call/jmp, never by writing it
rflags                 condition flags ("cc" in a clobber list)
gs                     segment base; on Windows it points at the per-thread TEB

Two habits to pick up from the tree's comments: call pushes the return address onto the stack, and rsp must stay 16-byte aligned at the point of a call — both rules come back in the JIT section below.

Inline asm — the grammar

GCC and Clang inline assembly is one statement with four parts:

the general form
asm volatile( "instructions, one string"
              : outputs      // "=r"(x)  — write result into x
              : inputs       // "r"(x)   — read x, any register;  "D"(x) pins rdi, "S"(x) pins rsi
              : clobbers);   // "cc" flags, "memory", and every register you destroyed

The rules that make it readable:

  • %%rsp — a real register is written with a doubled %, because a single % starts an operand placeholder. Operands are %0, %1… by position, or %[guest_rsp] by the name given in the constraint.
  • Clobbers are a promise to the compiler. If your asm writes rcx, the compiler must know — it is caller-saved, so it might be holding live data. Writing "memory" tells the compiler the asm can read or write any memory, which also stops it reordering your asm against other memory accesses (a compiler barrier).
  • volatile means "never delete or reorder this". A pure computation could be elided as dead code; a stack switch cannot.

Now the real thing. This is the Windows branch of the guest-thread entry from runtimeLinker.cpp, abridged and annotated. The context: guest_rsp points into guest memory, and this block must run the game's entry point on that stack, then come back:

src/loader/runtimeLinker.cpp — Windows, annotated
pushq %%r12 / %%r13 / %%r14 / %%r15   save the host callee-saved registers
movq  %%gs:0x08, %%r14                 read the Windows TEB stack limits...
movq  %%gs:0x10, %%r15
xorq  %%rcx, %%rcx
movq  %%rcx, %%gs:0x08                 ...and clear them, because stack probes during the
movq  %%rcx, %%gs:0x10                 guest run would otherwise check against host bounds
movq  %%rsp, %%r12                     park the host stack pointer
movq  %%rbp, %%r13                     and frame pointer
movq  %[guest_rsp], %%rsp              switch rsp to the guest stack
movq  %[guest_rbp], %%rbp              and rbp to the guest frame
callq *%[func]                         jump into the game (arguments already in rdi/rsi)
movq  %%r13, %%rbp                     restore host rbp
movq  %%r12, %%rsp                     restore host rsp
movq  %%r14, %%gs:0x08                 put the TEB stack limits back
movq  %%r15, %%gs:0x10
popq  %%r15 / %%r14 / %%r13 / %%r12   restore the callee-saved registers

Every line maps to a constraint on the right side of the statement. The inputs [guest_rsp] "r"(guest_rsp_reg) and [guest_rbp] "r"(guest_rbp_reg) feed the named %[...] operands; "D"(params) forces rdi and "S"(atexit_func) forces rsi, because that is where the System V caller placed them. The clobber list names every other register the block touches plus "cc" and "memory".

Explicit register variables

You can pin a C++ variable to a specific register, so the asm block can rely on it being there. Clang and GCC spell it as a register declaration with an asm name:

src/loader/runtimeLinker.cpp — macOS branch
register entry_func_t func_reg asm("rbx")      = func;
register uintptr_t    guest_rsp_reg asm("r14") = guest_rsp;
register uintptr_t    guest_rbp_reg asm("r15") = guest_rbp;

Why bother? The comment right above it explains the exact bug this prevents: on macOS, Clang can allocate a plain "r" input to r12/r13 — registers the asm block itself clobbers before consuming the value. Pinning the inputs to rbx/r14/r15 (registers the System V guest preserves) makes the hand-off safe.

`naked` functions and friends

Three attributes in this area appear exactly where you would expect them, and each means something specific:

AttributeMeansReal use
__attribute__((naked))no prologue or epilogue — the compiler emits only your asm body; you must end in ret yourselfRelocateHandlerReturnStub in runtimeLinker.cpp — the entire function is two instructions
__attribute__((noinline, returns_twice))never inline, and the function may return more than once (like setjmp) — it actually returns a second time when a fiber context is restoredFiberSaveContext in libKernel.cpp
__attribute__((noreturn))"control never reaches the end"FiberRestoreContext — it ends by jumping into saved code

Here is the naked stub in full — the whole function is its own epilogue, because its job is stack surgery:

src/loader/runtimeLinker.cpp:1115
__attribute__((naked)) static KYTY_SYSV_ABI void RelocateHandlerReturnStub() {
    asm volatile("addq $8, %rsp\n\t"   // drop the saved handler return address
                 "retq\n");            // return to whoever called the stubbed import
}

And the fiber save, which is the same idea as a setjmp: capture every callee-saved register and both stack pointers into a struct, then return 0 — later FiberRestoreContext loads them back and jmps to the saved return address, making FiberSaveContext "return" a second time with a different value:

src/libs/libKernel.cpp — FiberSaveContext, abridged
movq %[ctx], %%r10       struct pointer into a scratch register
movq %%rbx, 0(%%r10)     store every callee-saved register at a fixed offset
movq %%rbp, 8(%%r10)
movq %%r12, 32(%%r10)
...
leaq 8(%%rsp), %%r11     store rsp as it would be after this call returns
movq (%%rsp), %%r11      and the return address itself
xorl %%eax, %%eax        return 0

The ABI attribute is the C++ glue

The asm blocks above exist because guest code follows the System V ABI and the host build may follow Microsoft x64. The C++ side of that wall is two macros in src/common/abi.h — an attribute applied per function:

src/common/abi.h — in full
#define KYTY_MS_ABI   __attribute__((ms_abi))
#define KYTY_SYSV_ABI __attribute__((sysv_abi))

Any function the guest can call carries KYTY_SYSV_ABI, so the compiler emits a System V prologue for that one function. The attribute even travels on function pointers, which is how the JIT tells the compiler what convention a generated call must use:

src/loader/jit.h — a function pointer with the convention baked in
using func_t = KYTY_MS_ABI uint8_t* (*)();
// "a pointer to a function, called with the Microsoft convention, returning uint8_t*"

And a pointer can be manufactured from an address with reinterpret_cast, the only sanctioned way to turn a number into something callable:

auto* func = reinterpret_cast<entry_func_t>(addr);
func(params, atexit_func);

One ABI subtlety worth knowing before the JIT section: under System V, a variadic function reports how many vector registers are in use through the low byte of rax. That is why generated import thunks begin with push rax — the value must survive a call that may itself land in a variadic function. It is also why guestPrintf.cpp implements its own format-string interpreter: a System V argument list cannot be forwarded to a Microsoft-convention vprintf.

Machine code as data — jit.h

The strangest and most instructive file to read is src/loader/jit.h. Its structs are not described by machine code — their member uint8_t code[N] arrays are the machine code. The emulator writes bytes into these buffers at runtime and then calls them.

Start with the smallest one. A jmp with an index baked in:

src/loader/jit.h — JmpWithIndex
#pragma pack(1)

struct JmpWithIndex {
    void SetIndex(uint32_t index) { *reinterpret_cast<uint32_t*>(&code[1]) = index; }

    void SetFunc(void* handler) {
        auto func_addr = reinterpret_cast<int64_t>(handler);
        auto rip_addr  = reinterpret_cast<int64_t>(&code[10]);
        auto offset32  = static_cast<uint32_t>(static_cast<uint64_t>(func_addr - rip_addr) & 0xffffffffu);
        *reinterpret_cast<uint32_t*>(&code[6]) = offset32;
    }

    static uint64_t GetSize() { return 16; }

    // 68 00 00 00 00          push     <index>
    // E9 E0 FF FF FF          jmp      <handler>
    uint8_t code[16] = {0x68, 0x00, 0x00, 0x00, 0x00, 0xE9, 0x00, 0x00,
                        0x00, 0x00, 0x90, 0x90, 0x90, 0x90, 0x90, 0x90};
};

Three ideas to extract:

  • The struct is a template for instructions. code starts as the two instruction skeletons — 0x68 is push imm32, 0xE9 is jmp rel32 — with the operands zeroed and trailing 0x90 (nop) padding to a fixed size. #pragma pack(1) guarantees the struct has no padding, so &code[6] really is the rel32 operand.
  • Writing an operand is a cast to a pointer, then a store. *reinterpret_cast<uint32_t*>(&code[6]) = offset32; says: treat these four bytes as a uint32_t and store into them. No memcpy needed.
  • Relative offsets are computed in C++. The jmp's displacement is target − address_of_next_instruction. rip_addr = &code[10] is where rip will be after the jmp begins, so offset32 = func_addr − rip_addr is the exact value the CPU expects. The emulator is doing the arithmetic the assembler would do.

The next level is constructing objects inside a code buffer — placement new. CallPlt lays a table of JmpWithIndex stubs out at offsets into its own byte array:

src/loader/jit.h — CallPlt
explicit CallPlt(uint32_t table_size) {
    for (uint32_t index = 0; index < table_size; index++) {
        auto* c = new (&code[32] + JmpWithIndex::GetSize() * index) JmpWithIndex;
        c->SetIndex(index);
        c->SetFunc(this);
    }
}

new (address) Type runs the constructor on memory that already exists instead of allocating — here it initialises each JmpWithIndex at the right offset inside the code buffer, so that by the time the game runs, this struct is a runnable PLT.

The most elaborate one is SafeCall, a whole function hand-written in bytes, and it shows the two ABI rules from earlier being honoured by hand. Windows requires 32 bytes of shadow space and 16-byte stack alignment at a call:

src/loader/jit.h — SafeCall, the disassembly
sub    rsp, 0x80            make room to save every caller-saved register
pushfq                      preserve the flags
push   rcx / rdx / r8 / r9 / r10 / r11 / rbx / rdi / rsi
mov    rbx, rsp
and    rsp, 0xfffffffffffffff0    align the stack to 16 bytes
sub    rsp, 0x20                  reserve Win64 shadow space
movabs rcx, <handler>             the handler pointer is patched in at offset 0x22
call   rcx
mov    rsp, rbx                   restore, pop everything back, ret

Everything you need to read the tree is in that file: #pragma pack(1), reinterpret_cast writes, relative-offset arithmetic, placement new, and function pointers carrying their own ABI. Read it top to bottom once and the rest of the loader stops being opaque.

The red zone — a guest promise that breaks on Windows

System V grants a leaf function 128 bytes below rsp — the red zone — to use freely without adjusting the stack pointer. Guest code was compiled assuming that promise. Windows never made it: a kernel-delivered exception or signal handler will use that exact space, silently overwriting the guest's data.

Kyty's answer is src/loader/redZonePatcher.cpp, which reads .eh_frame to find function boundaries, identifies the functions that touch the red zone, and rewrites their memory instructions to route through a trampoline instead. The result struct is refreshingly honest about what it cannot fix:

src/loader/redZonePatcher.h
struct RedZonePatchResult {
    uint64_t function_count          = 0;
    uint64_t red_zone_function_count = 0;
    uint64_t patched_memory_instruction_count = 0;
    ...
    uint64_t unrelocatable_memory_instruction_count = 0;
};
Reading disassembly without a second monitor

The fastest way to check "what did this actually compile to" is Compiler Explorer: paste a function, pick x86-64 clang 18, and read the output column. For a KYTY_SYSV_ABI function you will see the first four integer arguments arrive in rdi rsi rdx rcx; drop the attribute and watch them move to rcx rdx r8 r9 instead. That visual is the whole calling-convention story in five seconds.

How a game loads & links

One diagram for the whole loading path: from the emulator opening eboot.bin, through mapping its segments, resolving every imported NID into the GOT, standing up the threads — to the running game reaching back through the GOT to call the console's libraries.

The seven boxes stay on screen the whole way. The module on disk is on the left; the runtime linker drives everything; the guest address space, GOT and HLE libraries fill in as it works; the threads and the running game come alive at the end. The three things that make it work

A NID is a name the game can carry without carrying the string. The PS5 module imports sceKernelAllocateDirectMemory as an 11-character hash of the name plus a per-library suffix. The loader hashes the same way to build its lookup table, so a lookup is a hash-map hit, not a string compare — and the shipped binary never contains the readable name.

The GOT is the entire indirection. The game's code doesn't know where sceKernelAllocateDirectMemory lives; it only knows which GOT slot holds its address. The linker fills that slot once, at load, with the address of KytyPS5's hand-written C++ function. From then on the game's call [GOT+n] jumps straight into native code with zero per-call overhead — which is why guest code can run at full speed while still being “emulated.”

A guest thread is a host thread. There is no scheduler to emulate. The main thread the loader creates is a real pthread with the guest's stack and a TLS block; the emulator's own GPU-submit and audio threads run alongside it. The only sleight of hand is the fs:[0] → Jit::Call9 patch that makes the guest's thread-local access work on your CPU.

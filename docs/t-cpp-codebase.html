The codebase map & the toolbox

Everything before this has pointed at files in passing. This page is the map you keep open: where each subsystem lives, how a run flows through it, and which third-party library does which job.

Read

Think of src/ as five layers with a clear dependency direction: common → loader/kernel → libs → graphics. Lower layers never depend on higher ones, which is exactly what keeps the map readable.

The entry points and boot sequence

A run flows through exactly these calls — this is the Lifetime animation in file form:

the boot chain, from argv to the game's main
main.cpp
  └─ ParseArgs()                    --game, the flag table from topic C3
  └─ Run(options)                   emulator.cpp
     └─ Init(...)                   the subsystem sequence from topic C5
     └─ MountSandboxDirs()          /app0, /temp0, ... — topic C5
     └─ LoadElf(eboot.bin)          runtimeLinker: parse SELF/ELF, dynamic tags
     └─ Execute(...)                emulator.cpp:152 — spawns the guest thread
        └─ RuntimeLinker::Execute() preload, resolve relocations, apply patches,
                                    run initialisers, call the entry point (topic C2's asm)
     └─ Graphics::WindowRun()       main thread parks here forever

Three files cover most "where does this happen" questions: emulator.cpp (the sequence), loader/runtimeLinker.cpp (the loading/execution), and common/subsystems.h (the lifecycle machinery that runs each step).

Two of them are the pair you saw in topic C2 and the patcher topics from the course: Zydis reads the guest's x86 instructions, and xbyak writes new ones. The emulator's own JIT in loader/jit.h is hand-assembled bytes; xbyak is the "proper" assembler used where a lot of code has to be generated.

Reading conventions that save time

  • Names map to hardware. pm4.h, gpu_defs.h, RegisterDefaults — if a name looks like a datasheet field, it is one. The codebase keeps console names rather than inventing friendly ones (the path.html appendix covers this in detail).
  • static = private to the file. Every HLE implementation is static; anything a subsystem exposes externally is declared in its header with a Lifecycle struct or a KYTY_SYSV_ABI function.
  • EXIT_IF/EXIT = the error channel. Topic C3's macros. A wall of them at the top of a function is a validation contract.
  • Follow a value, not a call graph. Start from a struct (a V#, a Submission, a KernelEvent) and grep for it — the tree is organised around data, and the data names are stable.
Where to start reading

If you want one linear path through the whole tree: main.cpp → emulator.cpp → common/subsystems.h → loader/runtimeLinker.cpp (load one module) → kernel/memory.cpp (allocate one page) → one libs/libPad.cpp function → one draw through commandProcessor. That is roughly the course's own order, and every later page is a deepening of one of those hops.

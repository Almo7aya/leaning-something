Shaders: RDNA 2 → SPIR-V

Games ship compiled RDNA 2 shader binaries. Vulkan wants SPIR-V. Translating the arithmetic is mechanical; recovering structured control flow from an unstructured branch soup is the actual problem, and the reason this is the largest single piece of the emulator.

Read

At snapshot 9992ab18, the recompiler is about 28,700 lines across 80 files. It is now organised as an explicit compiler pipeline: frontend/decode, frontend/cfg, frontend/translate, a typed value IR and its passes, then backend/spirv.

Important change from older Kyty material

The old decompiler/emitter layout and the separate scalar-provenance IR have been removed. TranslateProgram() now builds the typed IR directly through encoding-family opcode dispatchers, and SRT/resource analysis follows values in that IR. Do not look for ScalarProvenance.cpp, ShaderLaneMaskMode, or an ir.provenance field; none exists on current main.

Why it is hard, restated precisely

  • The input has no source-level structure. It is an instruction stream operating on scalar and vector registers, with no source variables or functions.
  • Control flow is hardware-shaped. Guest branches and execution masks must become SPIR-V selections and loops with declared merge and continue blocks.
  • Resources are computed values. A descriptor may be inline in user data or reached through shader resource-table loads, so binding requires tracing the shader's own address calculations.
  • Wave semantics differ. The guest assumes 32- or 64-lane waves and cross-lane operations; the host exposes Vulkan subgroups and their capabilities.
  • Failure can be visual only. A bad translation may draw the wrong pixels without crashing, which is why shader tests dominate the suite.

With --shader-log-direction File, Kyty writes decoded, CFG/IR, and SPIR-V material under _Shaders/. The main log also records decode, CFG, translation, and emission timings with the shader hash.

Decode, recover control flow, translate

frontend/decode/ShaderDecoder.cpp turns variable-length encodings into typed instructions from the SOP, VOP, SMEM, buffer, image, FLAT, LDS, and export families. frontend/cfg/ShaderCFG.cpp splits those instructions into blocks, computes graph facts, detects irreducible regions, and attempts to recover the merge and continue blocks SPIR-V requires.

Irreducibility or a failed Structurize() is a supported outcome. Kyty restores the unstructured graph and sets dispatcher_fallback; the SPIR-V backend then represents the shader as a loop around a program-counter dispatcher. This is slower, but it gives unsupported graph shapes an explicit fallback instead of silently miscompiling them.

frontend/translate is now a real frontend layer. Translate.cpp owns program setup while category files such as Scalar.cpp, Vector.cpp, and Memory.cpp dispatch decoded opcodes into typed IR operations.

One typed value IR

Translation initially permits register-like identities and control-flow joins. RewriteToSsa() establishes SSA form, then propagation, identity removal, and dead-code elimination simplify it. EliminateReadLane() removes cross-lane reads when a direct value is provably safe; if it rewrites anything, the simplification sequence runs again. Compute shaders also receive explicit shared-memory barriers where wave64 LDS semantics require them.

SRT planning, resources, and bindings

BuildSrtPlan() walks typed values to identify reachable shader-resource-table reads. Constant reads receive flattened offsets while genuinely dynamic reads stay explicit. TrackResources() then classifies buffers, images, samplers, access modes, formats, and sampled pairs.

Concrete resource data can come from a caller-supplied ResourceSnapshot or from MaterializeResources() reading current user data and guest memory. SpecializeResources() applies those facts to the IR; compilation and per-draw resource state therefore remain separate concerns.

AllocateBindings() covers ordinary buffers/images/samplers plus emulator support bindings:

enum class DescriptorBindingKind {
    Buffers,
    Sampled1D, Sampled2D, Sampled3D, ...,
    Storage1D, Storage2D, Storage3D, ...,
    Samplers, Gds,
    BdaPagetable, FaultBuffer,
    FlattenedSrt, UserData, Count,
};

BdaPagetable and FaultBuffer support buffer-device-address translation and recoverable RDNA2 FLAT-access faults. FlattenedSrt and UserData expose data that the guest ABI expected in scalar registers or tables. Finally, AnalyzeProgramRequirements() records the subgroup, derivative, LDS, scratch, and pixel-mask features emission must request.

Embedded vertex fetch

RDNA 2 has no conventional fixed-function vertex-input stage. A fetch prologue may load attributes into registers before the main vertex shader. When fetch_embedded is set, DetectEmbeddedVertexFetch() analyses the decoded instructions before translation and builds a Frontend::EmbeddedFetchPlan. That plan is passed through TranslateOptions::embedded_fetch, so translation emits the correct vertex-input operations directly; there is no later RewriteEmbeddedVertexFetches() pass.

Where the test weight is

ShaderRecompilerComputeTests.cpp is now about 1.13 MB and shaderCfgTests.cpp about 595 KB. The focused resource, scalar-tracing, stage-runtime, and vertex-metadata tests remain alongside them. The growth is useful evidence: shader behavior is specified most reliably by executable cases because a miscompile can produce only a visual error.

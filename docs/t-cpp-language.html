Appendix · C1

C++ language, by example

You already know how to program, so this is not a C++ course — it is a map of the small, dense subset of C++ this tree leans on. Every construct below appears within the first hour of reading, shown as it actually appears, not as a textbook would dress it up.

Read

C++ here is not trying to be clever. It is trying to do three things a garbage-collected language never asks of you: control the exact bytes of a struct, keep objects alive for a precise lifetime, and generate code at compile time instead of runtime.

The reading surface

Nearly everything is wrapped in a nested namespace, written with the C++17 shorthand. The nesting is organisational, not semantic — you can usually read the innermost name and ignore the rest:

src/kernel/memory.h
namespace Libs::LibKernel::Memory {   // Libs { LibKernel { Memory { ... } } }
  ...
}

using aliases replace typedef and are everywhere. The ones that look alarming are function-pointer aliases — read them right to left:

src/kernel/memory.h
using callback_func_t = void (*)(uintptr_t addr, size_t size);
//  "callback_func_t" is a pointer to a function that takes
//   (uintptr_t, size_t) and returns void.

And a file-local function is spelled static — the pre-C++ way of saying "internal linkage". Almost every HLE implementation in src/libs/ is static, so it exists only inside its own translation unit and the linker never exports it. If you see a function without static at file scope and it is not a class member, it is deliberately public.

`auto` — the default spelling

auto deduces the type from the initialiser. The tree writes const auto for anything read-only, const auto& to avoid copying, and auto* when the initialiser is a pointer. It never deduces a reference unless you write the & yourself:

src/loader/runtimeLinker.cpp
const auto aligned_stack_top = reinterpret_cast<uintptr_t>(stack_top) & ~static_cast<uintptr_t>(0x0f);
const auto guest_rsp         = aligned_stack_top - 2u * sizeof(uintptr_t);
src/libs/vaContext.h
auto* addr = reinterpret_cast<T*>(ptr);   // auto* keeps the pointerness

Think of auto as TypeScript's let x = ... where the type is always inferred — except there is no : Type annotation syntax for it. When a declaration says const auto&, read "a reference that I will not copy and cannot modify".

`constexpr` — computing at build time

constexpr marks a value (or function) that can be evaluated when the binary is built. src/loader/elf.h opens with a wall of them, because the ELF format's magic numbers never change:

src/loader/elf.h
constexpr char    ELFCLASS64    = 2;
constexpr int     EM_X86_64     = 62;
constexpr int     EV_CURRENT    = 1;
constexpr Elf64_Word PT_LOAD     = 1;
constexpr Elf64_Sxword DT_NEEDED = 0x00000001;
// a compile-time database of the format, used to parse game modules

Its partner is static_assert, which fails the build if the condition is false. The tree uses it as a contract on struct sizes — the ultimate guard against the compiler inserting padding you did not ask for:

src/kernel/memory.h
struct VirtualQueryInfo { ... };

static_assert(sizeof(VirtualQueryInfo) == 72, "VirtualQueryInfo struct size is incorrect");

Then the genuinely modern part. src/common/subsystems.h uses consteval (a function that must run at compile time), if constexpr (compile-time branching) and a requires clause (asking "does this type have a member?"):

src/common/subsystems.h
template <typename Lifecycle>
static consteval Callback ShutdownCallback() {
    if constexpr (requires { Lifecycle::shutdown; }) {
        return Lifecycle::shutdown;
    }
    return nullptr;
}

This is a type that may or may not provide a shutdown member; the code adapts at compile time instead of runtime. It feeds the wider pattern of a Lifecycle descriptor — a struct of static constexpr members that describes a subsystem to a registry:

src/kernel/memory.h
struct Lifecycle {
    static constexpr const char* name       = "Memory";
    static constexpr auto        initialize = Libs::LibKernel::Memory::Initialize;
    static constexpr auto        shutdown   = Libs::LibKernel::Memory::Shutdown;
};

static constexpr auto initialize = SomeFunction; stores a function pointer as a compile-time constant. No virtual dispatch, no runtime registration table — the compiler bakes the pointer in.

Templates — code that writes code

A template is a recipe instantiated at compile time for each combination of arguments. Three shapes appear constantly:

1. Function templates that deduce their own sizes. In OpcodeTable.h, the array size is captured by passing the array by reference — const Entry (&table)[N] — so FindOpcode works for any table without the caller saying how long it is:

src/graphics/shader/recompiler/frontend/decode/OpcodeTable.h
template <typename Entry, size_t N>
constexpr const Entry* FindOpcode(const Entry (&table)[N], uint32_t encoding) {
    for (const auto& entry: table) {
        if (entry.encoding == encoding) {
            return &entry;
        }
    }
    return nullptr;
}

2. Class templates with non-type parameters. Template arguments do not have to be types — they can be numbers. BitArray<N> is a fixed-size bit set, and the MultiLevelPageTable for the texture cache is configured entirely by numbers:

src/graphics/host_gpu/renderer/cache/multiLevelPageTable.h
template <typename EntryT, size_t PageBits = 20, size_t AddressSpaceBits = 40,
          size_t FirstLevelBits = 10>
class MultiLevelPageTable final {
    static_assert(AddressSpaceBits < 64);
    static_assert(PageBits < AddressSpaceBits);
    ...
};

3. Explicit specialisation. When one combination needs a hand-written version. vaContext.h has a bespoke reader for 32-byte float4 arguments that the generic path cannot handle:

src/libs/vaContext.h
template <>
inline VaFloatX4 VaArg_reg_save_area_fp<VaFloatX4, 32>(VaList* l) {
    // two 16-byte registers stitched into one float4
    ...
}

The takeaway: a template is not a function, it is a factory of functions. If the compiler cannot instantiate it for a given argument, the error lands at the call site — which is why template errors read backwards.

Move semantics and perfect forwarding

The single best example in the tree is src/common/uniqueFunction.h, a move-only, type-erased callable written in 54 lines. Read it once and three language features click into place:

src/common/uniqueFunction.h — the interesting half
template <typename Result, typename... Args>            // variadic template
class UniqueFunction {
    ...
    UniqueFunction(UniqueFunction&&) noexcept            = default;  // movable
    UniqueFunction(const UniqueFunction&)                = delete;   // not copyable

    template <typename Function>
    UniqueFunction(Function&& function)
        : m_callable(std::make_unique<Callable<std::decay_t<Function>>>(
              std::forward<Function>(function))) {}
    ...
};
  • Move-only. The copy constructor is = delete, the move is defaulted. A std::function copies; a UniqueFunction cannot, which is exactly the guarantee you want when a closure owns a resource (a buffer, a fence).
  • std::decay_t<Function> strips references and const from the deduced type so the stored member has a concrete, plain type.
  • std::forward re-applies the argument's original value category — lvalue stays an lvalue, rvalue stays an rvalue — so nothing is copied unnecessarily. std::move is the "I am done with this" cast; std::forward is the "pass it along as it came" cast.

The same trio appears in ByteBuffer, where Add(Byte&& val) lets the vector steal the byte instead of copying it. You do not need to write these yourself yet — you need to read them, and the rule that makes reading easy is: && in a parameter means "accept an rvalue and allow moving from it".

RAII — the object owns the resource

There is no garbage collector. A resource (memory, a Vulkan handle, a file) is owned by an object whose destructor releases it. std::unique_ptr is the default owner; std::shared_ptr is used when ownership genuinely must be shared.

src/graphics/host_gpu/renderer/cache/multiLevelPageTable.h
auto& bucket = m_first_level[FirstLevelIndex(page)];
if (bucket == nullptr) {
    bucket = std::make_unique<Bucket>();   // allocated lazily, freed by the table's destructor
    ++m_allocated_buckets;
}

And here is the deliberate use of shared_ptr, from the event-queue code (also covered in topic 12): a queue can be destroyed while another thread is blocked in it, so it is pinned with a shared reference for the duration of the operation:

using KernelEqueueRef = std::shared_ptr<KernelEqueuePrivate>;
[[nodiscard]] KernelEqueueRef KernelPinEqueue(KernelEqueue eq);

The mental model: every resource has exactly one owner, and the owner is a stack object whose lifetime you can trace by closing braces. When a function returns a unique_ptr or shared_ptr, the ownership is being transferred to the caller.

Casts — four kinds, one habit

Every C++ cast is an explicit conversion, and the four spellings communicate intent:

CastMeansIn this tree
static_castConvert between compatible typesinteger width changes: static_cast<uint32_t>(value), static_cast<uint32_t>(m_data.size())
reinterpret_cast"Treat these bytes as this type" — uncheckedpointer ↔ integer: reinterpret_cast<uintptr_t>(stack_top), reinterpret_cast<T*>(ptr). The workhorse of the whole project.
const_castDrop constrare; the signal is almost always "design smell nearby"
C-style (Type)xwhatever compilesstill common in src/libs/, e.g. (uint64_t)init_param in log lines

The one habit to build: reinterpret_cast is a promise with no runtime check. That is why the static_assert(sizeof(...)) guards from earlier exist — they are how you make an unchecked cast checked. When you see one, ask: what fixed layout is being relied on, and where is the assert?

Guest addresses are just integers

This is the single most important mental model for the codebase, and it is not a C++ feature — it is how C++ is used here. The game's memory lives in a 48-bit guest address space that the emulator lays out itself. Through most of the code, a guest address is an ordinary integer:

src/kernel/memory.h — the API surface
void     WriteBacking(uint64_t vaddr, const void* data, uint64_t size) noexcept;
void     InvalidateMemory(uint64_t vaddr, uint64_t size);
int      KYTY_SYSV_ABI KernelMprotect(const void* addr, size_t len, int prot);
uint64_t AllocateProgramMemory(uint64_t search_addr, uint64_t size, ...);

A real host pointer appears only at the boundary — when something must be executed or dereferenced. There the two worlds meet through reinterpret_cast:

auto* func = reinterpret_cast<entry_func_t>(addr);   // guest address → host function pointer
const auto aligned_stack_top =
    reinterpret_cast<uintptr_t>(stack_top) & ~static_cast<uintptr_t>(0x0f);

So the same eight bytes are a number in one function and a pointer in the next. Read any function that takes a vaddr/uint64_t argument as "this is an address in the guest, not a pointer into my process".

Raw memory and fixed layouts

An emulator constantly reinterprets bytes, so the tree is disciplined about layout. Four tools come up over and over:

1. #pragma pack(1) — turns off padding. The compiler inserts alignment padding between struct members; when the struct must mirror a file format or a wire layout, that padding is poison. src/loader/jit.h wraps its machine-code structs in #pragma pack(1), and vaContext.h does the same for its register-save area.

src/libs/vaContext.h
#pragma pack(1)

struct VaList {
    uint32_t gp_offset;
    uint32_t fp_offset;
    void*    overflow_arg_area;
    void*    reg_save_area;
};

#pragma pack()

2. Bitfields — flags packed into a single word by declaring a bit width:

src/kernel/memory.h
struct VirtualQueryInfo {
    ...
    uint32_t is_flexible  : 1;
    uint32_t is_direct    : 1;
    uint32_t is_stack     : 1;
    uint32_t is_pooled    : 1;
    uint32_t is_committed : 1;
    uint32_t is_gpu_prt   : 1;
    uint32_t amm_usage    : 1;
    uint32_t reserved     : 1;
    char      name[KERNEL_MAXIMUM_NAME_LENGTH];
    uint8_t   gpu_mask_id;
    uint8_t   reserved2;
};

static_assert(sizeof(VirtualQueryInfo) == 72, "VirtualQueryInfo struct size is incorrect");

Bitfields are fine inside the emulator where host and guest are the same compiler — but the layout rules are implementation-defined, so you never rely on them across the ABI boundary. Where the guest's layout must match byte-for-byte, the tree uses static_assert to prove it.

3. Anonymous unions — several views of the same bytes, selected by a tag. The memory-pool batch entry is one 32-byte record whose meaning depends on op:

src/kernel/memory.h
struct KernelMemoryPoolBatchEntry {
    uint32_t op;
    uint32_t flags;
    union {
        struct { void* addr; uint64_t len; uint8_t prot; uint8_t type; } commit;
        struct { void* addr; uint64_t len; } decommit;
        struct { void* dst;  void* src;  uint64_t len; } move;
        ...
        uintptr_t padding[3];
    };
};

4. offsetof — the byte offset of a member within a struct. vaContext.h uses it to build a hand-rolled variadic-argument reader by offset arithmetic on the register save area.

src/libs/vaContext.h — inside the VA_CONTEXT macro
(ctx).va_list.gp_offset         = offsetof(VaRegSave, gp);
(ctx).va_list.fp_offset         = offsetof(VaRegSave, fp);

The preprocessor as a code generator

Modern C++ avoids macros, but this codebase uses them deliberately in three places — and you must read them to read the libraries:

1. Special-member boilerplate. Deleted copy/move constructors for a whole class in one line:

src/common/common.h
#define KYTY_CLASS_NO_COPY(name)                                                       \
public:                                                                                 \
    name(const name&)                = delete;                                         \
    name& operator=(const name&)     = delete;                                         \
    name(name&&) noexcept            = delete;                                         \
    name& operator=(name&&) noexcept = delete;

2. The HLE registration DSL. The whole of src/libs/ is registered with a handful of macros (covered in topic 12 and animated below). Notice the # operator in LIB_ADD — it stringifies its argument at compile time, turning a function name into a log label with no reflection machinery:

src/libs/libs.h
#define LIB_ADD(n, f, t)                                                       \
    {                                                                          \
        Loader::SymbolResolve sr {};                                           \
        sr.name  = n;  sr.library = g_library;  sr.module = g_module;          \
        ...
        auto        func     = reinterpret_cast<uint64_t>(f);                  \
        const char* dbg_name = "" #f;        // "function_name" as a string \
        s->Add(sr, func, dbg_name);                                            \
    }

#define LIB_FUNC(n, f) LIB_ADD(n, f, Loader::SymbolType::Func)

3. ABI shims that must be spelled identically at every call site — VA_ARGS expands to the System V argument list, VA_CONTEXT to the code that captures it into a struct.

Reading a macro: expand it in your head, pasting the arguments into the body. The \ at line ends just means "this macro continues on the next line". __func__, seen inside PRINT_NAME(), is a built-in that is always the current function's name — the macro-compatible alternative to a template __FUNCTION__.

And the thread_local in LIB_NAME is worth calling out: each translation unit gets its own per-thread flag, which is how PRINT_NAME_ENABLE(true) can turn on tracing for one module on one thread without flooding the log from everywhere else.

One habit to break

In JS, const obj = { ... } gives you a mutable reference — the word const lies. In C++, const is enforced: const T& cannot be modified, and the compiler will not let you forget it. When C++ code seems to be fighting you about const, it is usually telling the truth about an ownership question you should stop and think about.

Concurrency & the memory model

The emulator is four threads doing four completely different jobs, sharing one address space. This page is the map: who runs what, how work gets from one thread to another, and the C++ primitives — atomics, locks, condition variables, timeline semaphores — that hold it together.

Read

For a web engineer the closest analogy is a service worker plus a render thread plus a worker pool sharing a page — except here there is no runtime to arbitrate, and a mistake corrupts the whole process.

The four threads

Three of them are created before a single instruction of the game runs. The main thread drives the window and SDL; the guest thread runs the game itself; the GPU thread parses PM4 and drives Vulkan; and the audio thread mixes and plays back. This is the guest and GPU pair, both from emulator.cpp and graphicsRun.cpp:

src/emulator.cpp — the guest thread, then the main thread parks
static void Execute(const std::filesystem::path& game_patch) {
    Common::Thread guest_thread(
        [](void* param) {
            auto* rt = Common::Singleton<Loader::RuntimeLinker>::Instance();
            rt->Execute(*static_cast<const std::filesystem::path*>(param));
        },
        &patch_path);
    Libs::Graphics::WindowRun();   // main thread never returns from here
    std::quick_exit(0);
}
src/graphics/guest_gpu/graphicsRun.cpp — the GPU thread
GpuState::GpuState(RenderContext& renderer): m_renderer(renderer) {
    m_gfx_cp = std::make_unique<CommandProcessor>(renderer);
    m_thread = std::jthread(ThreadRun, this);   // one dedicated GPU thread
}

Note the two thread wrappers in one file: the guest thread uses Common::Thread (the project's own wrapper, so it can keep a unique per-thread id for logs and TLS), while the GPU thread uses std::jthread (C++20, joins automatically on destruction). Both run on the same host process — a guest crash is a real crash in this process (see topic C3).

Handing work between threads

The guest never touches Vulkan directly. It fills PM4 buffers and calls GpuState::SendCommand, which has the classic "run inline if you're already on the right thread, otherwise queue it" shape:

src/graphics/guest_gpu/graphicsRun.cpp — the handoff
void GpuState::SendCommand(Common::UniqueFunction<void>&& command) {
    if (IsGpuThread()) {
        command();                    // already on the GPU thread: run now
        return;
    }
    Common::LockGuard lock(m_queue_mutex);
    m_commands.push_back(std::move(command));
    m_work_available.Signal();        // wake the GPU thread
}

Two ideas worth absorbing:

  • The lock is held only to push onto the queue, never while running. m_commands is guarded by m_queue_mutex; the actual work happens outside the lock on the GPU thread. That is the difference between a queue and holding a lock across a long operation.
  • A condition variable is the wake-up. m_work_available lets the GPU thread sleep when idle and wake exactly when work arrives, instead of busy-polling. The GPU thread's whole job is a loop: wait for signal, pop a submission, process it.

The GPU thread actually serves 57 queues — one graphics queue plus seven compute pipes × eight queues each:

src/graphics/guest_gpu/graphicsRun.cpp
static constexpr uint32_t ComputePipeCount     = 7;
static constexpr uint32_t QueuesPerComputePipe = 8;
static constexpr uint32_t QueueCount           = 1 + ComputePipeCount * QueuesPerComputePipe;
std::array<std::deque<Submission>, QueueCount> m_queues;

The guest submits to a specific queue the way it would on real hardware; Kyty keeps them separate and round-robins its single worker across them. That is a faithful model of a thing it is not physically reproducing.

Atomics and memory order

The tree uses std::atomic for counters that must never tear, and almost always with the default sequential consistency — except where it consciously relaxes. The canonical relaxed example is the log throttling in shader.cpp:

src/graphics/shader/shader.cpp — a deliberately relaxed counter
static std::atomic_uint log_count {0};
if (log_count.fetch_add(1, std::memory_order_relaxed) < 32) {
    // print the same warning at most 32 times, from any thread
}

Why relaxed is correct here and scary elsewhere:

  • Relaxed guarantees the operation is atomic and won't be reordered around its own other atomics, but gives no ordering against unrelated memory. Fine for "count how many times this happened" — the count can be a few off and nobody cares.
  • Sequential consistency (the default when you write no order) additionally gives a single global order of all seq-cst operations. That is what you want when a counter signals something — like m_pending_commands, which another thread observes to decide whether the GPU is still busy.

The rule to take away: a counter that only counts can be relaxed; a flag or counter that coordinates must not be. When in doubt, write nothing (the default is safe), and only relax after you can say exactly why.

The coherency channel — the cross-thread handshake

CPU and GPU share one memory in the guest's model. On the host, the GPU thread must see what the guest thread wrote. The emulator's trick (covered properly in topic 10) is that the GPU never polls — it faults. When the guest writes a page the GPU has been told about, a host page-fault fires on the faulting thread, and the exception handler routes it to the memory layer:

src/loader/runtimeLinker.cpp — the exception handler, routing to memory
if (Libs::LibKernel::Memory::HandleGpuFault(access, info->access_violation_vaddr)) {
    return true;   // the fault was a coherency notification, not a bug
}

This is concurrency working through the memory system: the page protection is the lock, the fault is the signal, and no queue or mutex is involved. On Linux and macOS the handler runs on a per-thread 64 KB alternate signal stack (InitializeThreadSignalStack) so the fault can still be delivered when the guest stack page is write-protected. It is the single most distinctive thing about this codebase, and it is why reinterpret_cast and page-granular thinking dominate.

The GPU's own clock: fences & timeline semaphores

Between the GPU thread and the Vulkan driver, ordering is expressed with semaphores. The renderer submits with wait ticks and signal ticks — a Vulkan timeline semaphore, a monotonically increasing counter the GPU advances as work completes:

src/graphics/host_gpu/renderer/commandScheduler.cpp — a submission with ticks
n_info.waitSemaphoreValueCount   = submit.num_wait_semaphores;
n_info.pWaitSemaphoreValues      = submit.wait_ticks.data();
n_info.signalSemaphoreValueCount = submit.num_signal_semaphores;
n_info.pSignalSemaphoreValues    = submit.signal_ticks.data();

The reason the game and GPU can overlap is that several submissions are in flight at once. Each command buffer carries a monotonic timeline tick; MasterSemaphore reports the latest completed value, and deferred objects are released only after their tick passes. CommandPool starts in batches of four and grows by four when no completed buffer is reusable, instead of rotating through a fixed fence-backed pool.

The mental model

Guest threads = host threads. Guest mutexes/events = host mutexes/events under a thin shim. The GPU thread = a dedicated worker consuming queues and driving Vulkan. And the coherency layer = memory protection doing the synchronisation the guest believes the hardware provides for free. If you keep those three layers separate, every concurrency bug you meet will fall into one of them.

How the guest runs

One frame, from the game's point of view. The game doesn't know it's emulated: it updates its world, uses its heap and threads, builds PM4 command buffers and flips — all as native code. The only moments it leaves its own instructions are the sce* calls through the GOT.

What the guest never notices

It runs at native speed. There is no interpreter between the game and your CPU. The update loop, the physics, the AI — all of it is the game's own x86-64 executing directly. The cost of “emulation” is paid only at the boundaries: the sce* calls and the GPU work.

It talks to a console that isn't there. Every service is a normal function call — sceKernelAllocateDirectMemory, sceGnmSubmitCommandBuffers, sceVideoOutSubmitFlip — that happens to land in KytyPS5's C++ instead of Sony's firmware. The game builds real PM4 packets and hands over real shader binaries, exactly as it would on hardware.

It is a normal multithreaded program. Its worker threads are host threads; its locks are umtx wait/wake; its memory is a heap it manages itself. The emulator adds no scheduler and no memory model of its own — it just provides the console-shaped functions the game already expects.

The mirror image — everything the emulator does to answer these calls — is the host side. And you loaded here from how a game loads & links.

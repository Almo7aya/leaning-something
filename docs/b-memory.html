A value, its address and an alias

int counter = 3; creates an object. &counter obtains its address. int* pointer stores an address of an integer; *pointer accesses the pointed-to integer. In int& alias = counter, the ampersand instead declares a reference: another name for that object. Assigning to alias changes counter, not which object the reference denotes.

A pointer may be null, but reading through a null, dangling or otherwise invalid pointer is not allowed. A reference also requires a live object; it does not keep that object alive. const int* prevents changing the integer through that pointer; int* const prevents changing the pointer itself. Neither spelling proves ownership or thread safety.

Storage and lifetime are different questions

A local object with automatic storage duration is destroyed when its scope ends; this is often described as a stack object. A dynamically allocated object can outlive the function that created it. Someone must eventually release it. RAII ties resource cleanup to an owning object's lifetime: its destructor performs cleanup. A destructor is the function named ~Type(), called when that object is destroyed.

std::unique_ptr<Buffer> owns one dynamically allocated Buffer. std::make_unique constructs it. The owner itself may be local, a member, or stored in another object. std::shared_ptr is a different policy: several handles share ownership, and the last strong owner releases the object. Cycles of shared ownership need additional care. RAII does not require every resource to have a single stack owner.

std::vector<int> owns a resizable sequence. std::span<const int> borrows its elements without owning or extending their lifetime. A vector reallocation can invalidate a view even while the vector object remains alive. A span is not a bounds-checking or lifetime-enforcing system in C++20.

Transfer the owner, keep track of the object

auto asks the compiler to deduce a variable's type from its initializer; it does not make the variable dynamically typed. owner->values accesses a member through a pointer-like owner. std::move(owner) permits a move; the receiving unique_ptr actually performs the transfer. The old unique_ptr becomes empty, while the Buffer stays at the same address. Moving arbitrary types has type-specific effects; do not generalize the empty unique_ptr rule to every moved-from object.

Complete runnable teaching program · ownership.cpp

#include <iostream>
#include <memory>
#include <span>
#include <utility>
#include <vector>

struct Buffer {
    std::vector<int> values{10, 20, 30};
    ~Buffer() { std::cout << "buffer destroyed\n"; }
};

int main() {
    int counter = 3;
    int* pointer = &counter;
    int& alias = counter;
    *pointer = 4;
    alias = alias + 1;
    std::cout << "counter=" << counter << '\n';
    {
        auto owner = std::make_unique<Buffer>();
        std::span<const int> view(owner->values);
        auto next_owner = std::move(owner);
        if (owner || !next_owner || view.size() != 3 || view[1] != 20) return 1;
        std::cout << "borrow=" << view[1] << '\n';
        std::cout << "old owner empty=" << std::boolalpha << !owner << '\n';
        // Do not resize the vector or destroy next_owner while using view.
    }
    std::cout << "scope ended\n";
    return counter == 5 ? 0 : 1;
}

Exercise

Draw boxes for counter, the two owner handles, the Buffer, its vector elements and the span. Draw arrows after the move. Then change std::span<const int> to std::span<int>, assign 25 to element 1 before moving the owner, and update the expected check/output. Explain why the original const view rejects the assignment.

Hint

The unique_ptr move changes the owning handle, not the allocation. A span points to elements, not to the owner variable.

Worked answer and rubric

The pointer and alias both reach counter, whose final value is 5. next_owner owns Buffer after the move; owner is empty. The view still reaches the original vector elements. The mutable-view edit prints borrow=25; change the internal check accordingly. When the block ends, next_owner destroys Buffer and its vector. Never demonstrate the invalid case by actually dereferencing view after destruction; explain the invalidation instead. You are ready when you can identify who destroys each object and which operation invalidates each borrow.

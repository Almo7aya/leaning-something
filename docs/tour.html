Anatomy of a PlayStation 5 emulator

KytyPS5 takes a program compiled for a games console — a machine with its own operating system, its own graphics API, and its own idea of what memory looks like — and persuades it to run on a Windows, Linux or x86-64 macOS host. 01

What an emulator like this actually does

The word "emulator" suggests simulating a chip instruction by instruction. KytyPS5 does almost none of that, and understanding why is the single most useful thing to grasp before reading any code.

The PS5 is a PC in an unusual coat

The console's CPU is an 8-core AMD Zen 2 running the x86-64 instruction set — the same instruction set as the machine you are reading this on. Its GPU is AMD RDNA 2, the same architecture as a Radeon RX 6000 card. Its operating system is a derivative of FreeBSD.

That means a compiled PS5 game is already machine code your processor can execute. There is no interpreter, no dynamic recompiler, no basic-block cache anywhere in this repository. The emulator maps the game's code into memory, sets the CPU's instruction pointer to the entry point, and lets the silicon run it.

The consequence

Because the CPU is free, all the difficulty moves elsewhere: to the calling convention, to the memory layout, to the thousands of operating-system functions the game calls, and above all to the GPU. Nearly half of the codebase is graphics.

The four boundaries that must be bridged

Everything in this project is one of four translations. The colour coding used throughout this page follows them.

Guest — the PS5 and its software Kyty — the emulator's translation layer Host — the real PC, OS and GPU
The four translation problemsselect a tab

The instructions are identical. The conventions are not. The PS5 uses the System V AMD64 calling convention (arguments in rdi, rsi, rdx, rcx, r8, r9). Windows uses the Microsoft x64 convention (rcx, rdx, r8, r9, plus 32 bytes of shadow space). A guest function calling an emulator function would otherwise pass its arguments into the wrong registers.

Kyty solves this by annotating every function the guest can call with a Clang attribute, so the compiler generates a System V prologue for that one function while the rest of the emulator stays native:

#define KYTY_MS_ABI   __attribute__((ms_abi))
#define KYTY_SYSV_ABI __attribute__((sysv_abi))

This is also why the build refuses MSVC's cl.exe and requires clang-cl — MSVC has no such attribute. There is a second gap too: PS5 code reads thread-local storage through the fs segment register, which Windows reserves for itself. That one is solved by rewriting the guest's instruction bytes; see §04.

src/common/abi.hCMakeLists.txt

The game expects specific addresses to be available. PS5 software allocates at fixed regions, uses 16 KB pages where the host uses 4 KB, and distinguishes "direct" (physical) memory from "flexible" (virtual) memory in ways Windows and Linux do not.

Kyty therefore reserves whole bands of the host address space up front and hands them out itself, keeping its own page tables so it can answer the guest's queries about protection, type and naming. On macOS it goes further and uses linker flags to pin segments of the emulator binary itself so the required ranges are never taken by the system loader.

src/kernel/memoryAddressSpace.incsrc/kernel/memory.cpp

Every system call has to be answered by something. A game calls scePthreadCreate, sceKernelOpen, sceAudioOutOutput, sceNpWebApiCreateContext — thousands of distinct entry points across dozens of modules.

Kyty implements them in native C++ (this is called high-level emulation, or HLE) rather than running Sony's real system libraries. A guest call to "create a thread" becomes a real host thread; "open a file" becomes a real host file handle inside a sandboxed directory tree. The src/libs/ directory is 41,500 lines of exactly this.

src/libs/src/kernel/

This is the hard one. The game does not call a graphics API that Kyty can implement function-by-function. It builds raw command packets in memory — the same binary format the real GPU's command processor reads — and hands the buffer to the kernel.

So Kyty must implement a software model of an AMD command processor: parse PM4 packets, maintain the ~4,000 hardware registers they write, and when a draw packet arrives, translate the entire accumulated register state into a Vulkan pipeline. And the shaders inside are RDNA 2 machine code that must be decompiled and re-emitted as SPIR-V. Sections 08–10 are about this.

HLE versus LLE, in one paragraph

Low-level emulation means running the console's real firmware and libraries on a simulated machine — maximally accurate, extremely slow, and legally fraught because it requires copyrighted system files. High-level emulation means reimplementing what those libraries do. KytyPS5 is HLE throughout; its README notes that "no external low-level emulation modules are currently required." The trade-off is that every unimplemented function is a potential crash, and behaviour can differ from the real console in subtle ways.

Two threads own the process

Note what Execute() does: it spawns a thread for the guest, then the main thread runs the window event loop forever. This inversion is deliberate. The loader: turning a file into a running program

A PS5 executable is an ELF file with Sony's extensions bolted on. The loader in src/loader/ is about 6,200 lines but it is where most of the genuinely clever tricks live.

The file format

Games ship an eboot.bin, which is a SELF — a Signed ELF, a small container header followed by (on retail discs, encrypted) ELF segments. Kyty parses the container, then the ELF inside. The ELF is standard x86-64 ELF64 with FreeBSD's OS/ABI marker, but with Sony-specific type and tag values:

Mapping it into memory

LoadProgramToMemory() walks the program headers, computes the total span, rounds it to the guest's 16 KB page size (0x4000), and reserves that much guest memory. Modules are laid out sequentially from a fixed base:

constexpr uint64_t SYSTEM_RESERVED  = 0x800000000;
constexpr uint64_t CODE_BASE_OFFSET = 0x100000000;
constexpr uint64_t CODE_BASE_INCR   = 0x010000000;

// first module lands at 0x900000000, each subsequent one 256 MB further on
static uint64_t g_desired_base_addr = SYSTEM_RESERVED + CODE_BASE_OFFSET;

Each PT_LOAD segment is read from the file to p_vaddr + base_vaddr, then given its final page protection. Executable segments get an extra pass first — PatchProgram() — before protection is applied and the instruction cache is flushed.

Patching the guest's instruction bytes

This is one of the most instructive functions in the project. Two patterns in PS5 code cannot execute on Windows, so the loader scans the guest's .text and rewrites them in place.

1 · Thread-local storage through fs:[0]

PS5 code reads its thread control block with mov rax, qword ptr fs:[0]. On Windows the fs segment belongs to the OS and points somewhere else entirely. The loader finds every such instruction and overwrites those exact 9 bytes with a call to a generated stub, which fetches the guest's real TCB pointer and returns it in the same register the original instruction targeted:

// before — 9 bytes
64 48 8B 04 25 00 00 00 00     mov rax, qword ptr fs:[0]

// after — same 9 bytes
48 E8 xx xx xx xx              rex.w call tls_handler
48 89 C0                       mov  rax, rax

The leading 48 (REX.W) on the call is deliberate: any 0x66 operand-size prefix in front of the original instruction is left in place, and an AMD CPU would otherwise honour it and execute a 16-bit callw. The REX prefix neutralises it on every vendor, which is why the trailing nop of earlier builds is gone (Jit::Call9).

The stub itself is hand-assembled machine code in jit.h. Because the emulator is compiled with the Microsoft ABI on Windows but the guest runs System V, the stub (SafeCall) pushes the flags and all volatile registers, aligns the stack to 16 bytes, reserves 32 bytes of Win64 shadow space, calls the C++ handler, then restores everything.

2 · The stack canary store

Compiler-generated stack-protector code stores through fs:[0x28]. Since fs is wrong, this would fault at address 0x28. The loader replaces the 12-byte store with nops — and, if it recognises the specific "canary failed → ud2" epilogue that follows, replaces the whole thing with pop rbp; ret.

NIDs: how symbols are named

PS5 modules do not export readable symbol names. They export NIDs — an 11-character base64-ish encoding of a hash of the original name, followed by the library and module it belongs to, separated by #:

lUwEK9UwLNo#libSceGnmDriver#libSceGnmDriver
└─ symbol ─┘ └─── library ───┘ └──── module ────┘

RuntimeLinker::Resolve() splits on #, maps the library and module identifiers back through the file's own tables, and then searches, in order: the HLE symbol database, then the export tables of every other loaded guest module.

The HLE side registers its functions with a pair of macros. This is the entire mechanism by which the emulator "implements" a console function:

LIB_VERSION("Graphics5", 1, "Graphics5", 1, 1);

LIB_DEFINE(InitAgcDriver_1) {
    LIB_FUNC("23LRUSvYu1M", Gen5::AgcInit);
    LIB_FUNC("f3dg2CSgRKY", Gen5::AgcCreateShader);
    LIB_FUNC("k3GhuSNmBLU", Gen5::AgcCbDispatch);
}

LIB_FUNC expands into a SymbolResolve record — name, library, library version, module, module major/minor version, type — and inserts the address of the native C++ function into the shared database. When the guest's relocation for that NID is processed, the address of Kyty's C++ function is written into the guest's Global Offset Table. From then on, the guest calls straight into the emulator.

What happens when a symbol is missing

Real games import functions Kyty has never heard of. Rather than aborting, the loader generates a 165-byte thunk per unresolved import and points the relocation at it. When the guest eventually calls it, the thunk:

  1. Pushes rax and all six System V argument registers, plus all eight xmm registers, onto the stack — so the original arguments survive.
  2. Loads a record ID into rdi and calls ResolveImportStubWithId, which retries resolution now that more modules may be loaded.
  3. Restores every register exactly.
  4. If a real address came back, jmp to it — the original call proceeds as though nothing happened. If not, xor eax, eax; ret: return zero and hope the game copes.
Why this design

Failing at load time would make almost every game unbootable, because games import far more than they call. Failing lazily at call time means only the code paths actually taken can break — and the log records which NID was stubbed, which is exactly what a compatibility bug report needs.

Deep dive · why the Windows stack is pre-grown by 768 KB

Windows commits thread stacks lazily using a guard page: touching it triggers an exception that commits another page and moves the guard down. This requires that code touch the stack in order, which is why MSVC emits __chkstk probes for large frames.

PS5 code has no such probes. A guest function with a large local array can write past the guard page, and Windows will then treat that as a genuine stack overflow. Module initialisers also run on the host stack before the guest's own stack is in use.

So before any guest code runs, RuntimeLinker::Execute() deliberately walks the guard page down 768 KB by writing a zero to it in a loop, forcing Windows to commit the whole region up front.

size_t expanded_size = 0;
while (expanded_size < 768 * 1024) {
    sys_dbg_stack_info_t stack {};
    SysStackUsage(stack);
    *reinterpret_cast<uint32_t*>(stack.guard_addr) = 0;   // force commit
    expanded_size += stack.guard_size;
}

Memory: the address space is part of the ABI

On a console the memory map is documented and games rely on it. Kyty reserves matching bands of the host address space and runs its own allocator inside them.

Keeping the CPU and GPU in agreement

This is the subtlest problem in the whole emulator, and it deserves its own explanation.

On a real PS5, CPU and GPU share one physical memory. When a game writes vertex data with the CPU and then draws with it, no synchronisation is needed — the GPU reads the same bytes. On a PC, the GPU has its own memory, and Vulkan resources are copies. Kyty must detect when a copy has gone stale.

It does this with hardware page protection. Two classes cooperate:

PageManagerkytyOwns the actual protection calls. UpdatePageWatchers(track, vaddr, size, mode) makes a guest range write-protected (or read-write-protected). A guest access then faults, and the fault lands in the exception handler from §04.
↓ reports dirtiness
MemoryTrackerkytyDivides the address space into fixed regions, each with per-page dirty bits tagged by source: DirtySource::Cpu or DirtySource::Gpu. Answers IsRegionCpuModified() / IsRegionGpuModified() and drives the upload and download loops.

The result is a two-way flow, both driven by page faults rather than by the game telling anyone anything:

  • Upload — before a draw reads a texture, ForEachUploadRange() finds the sub-ranges the CPU dirtied since the last upload, copies just those to the Vulkan image, then flips those pages to GPU-owned and re-protects them.
  • Download — when the GPU has written a render target and the CPU later reads it, ForEachDownloadRange() copies back only the ranges the GPU marked dirty.

The tracker is defensive about its own invariants. It refuses re-entry from inside an upload callback (CheckNotInUploadCallback) and hard-fails if an invalidation leaves GPU-owned pages behind — bugs here produce corruption that is otherwise almost impossible to localise.

The kernel layer

Nearly twelve thousand lines implementing the FreeBSD-derived services a PS5 game assumes it is running on.

Threads — the largest single file after the PM4 handlers

src/kernel/pthread.cpp is 130 KB. It is a full pthread implementation: threads with names and priorities and CPU affinity masks, mutexes with all four types and protocol attributes, condition variables, read-write locks, thread-specific keys with destructors, cancellation with both deferred and asynchronous types, and per-thread signal queues.

Guest threads are real host threads, but with two extra pieces of state Kyty must maintain itself:

  • A guest stack allocated inside the guest address space, because guest code computes addresses relative to its own stack and those addresses can be handed to the GPU or stored in structures the emulator inspects. PthreadCreateMainGuestStack() sets this up for the main thread before the entry point runs.
  • A thread control block reachable from the patched TLS stub, plus a per-thread copy of every loaded module's TLS image. RuntimeLinker::TlsGetAddr() lazily allocates these; DeleteTlss(thread_id) frees them on exit.
src/kernel/pthread.hsrc/loader/runtimeLinker.cpp:1923

Event queues

sceKernelCreateEqueue and friends are a kqueue-shaped API: a game creates a queue, attaches sources to it (a vertical-blank event, a flip event, a timer, a user event), then blocks in sceKernelWaitEqueue. Kyty routes internal events — notably the display driver's flip and vblank notifications — into these queues.

Lifetime here is genuinely hard: a queue can be destroyed while another thread is blocked on it, or while the graphics thread is mid-way through delivering an event. There is a dedicated 19 KB test file for exactly this.

The pragmatic pattern

Anatomy of a PM4 packet

The stream is a sequence of 32-bit dwords. Each packet starts with a header dword whose top two bits give the packet type; everything Kyty handles is type 3. Decode one yourself:

PM4 type-3 header decoderedit the hex value

Field extraction, straight from the source: type = cmd_id >> 30, opcode = (cmd_id >> 8) & 0xff, body length = ((cmd_id >> 16) & 0x3fff) + 1 dwords. Bits 7:2 carry a Sony-specific sub-selector used when the opcode is IT_NOP. src/graphics/guest_gpu/pm4.cpp:122

Dispatch by jump table

With ~50 opcodes and thousands of register offsets, a switch statement would be unmanageable. Instead Kyty builds four function-pointer tables at start-up and indexes them directly:

extern const std::array<cp_op_parser_func_t, 256>        g_cp_op_func;         // by opcode
extern const std::array<hw_ctx_parser_func_t, CX_NUM>   g_hw_ctx_func;       // context registers

Tiling: the layout problem

GPUs do not store textures row by row. They interleave pixels into small blocks so that a 2D neighbourhood lands in one cache line. AMD's schemes have names like Standard 4 KB, Standard 64 KB, PRT 64 KB, Render-Target 64 KB and Depth 64 KB, each with a different swizzle and different alignment rules per bytes-per-pixel and per mip level.

Guest memory holds tiled data; Vulkan wants linear data (or its own opaque tiling). tile.cpp — 52 KB of address arithmetic — computes sizes, offsets, mip layouts and the XOR swizzles. The actual conversion runs on the host GPU as compute shaders, one per layout family:

Graphics II — the shader recompiler

About 29,000 lines across 84 files under recompiler/ turn RDNA 2 machine code into SPIR-V. Current main has an explicit frontend/decode → frontend/cfg → frontend/translate → typed SSA IR → backend/spirv architecture.

Why it is hard

  • The input is machine code, not source. There are no source variables or functions, only packed instructions and scalar/vector registers.
  • GPU control flow is unstructured. RDNA 2 uses an execution mask: a 64-bit register where each bit enables one lane. Branches manipulate this mask. SPIR-V, by contrast, demands structured control flow — every branch needs a declared merge block, every loop a header and a continue target.
  • Resources are opaque. A texture is a 256-bit "T# descriptor" the shader loads out of memory at runtime. To emit a Vulkan descriptor binding, the compiler must trace backwards to work out where that descriptor came from.
  • Wave size differs. RDNA 2 shaders assume waves of 32 or 64 lanes and use cross-lane instructions. Host GPUs have their own subgroup sizes.
The compilation pipelineclick a stage

TranslateProgram() and CompileProgram() are the reading map. The first runs decode → CFG → translate → SSA and simplification → SRT plan → resource tracking and returns an immutable TranslateResult; the second applies a ResourceSpecialization, collects shader info, allocates bindings, analyses requirements and emits SPIR-V. Their phases log elapsed milliseconds and a shader hash. For ShaderType::Mesh — merged ES/GS geometry stages, run as VK_EXT_mesh_shader mesh shaders — DecodeFusedProgram() joins the front and back stage code first. Failures EXIT; nothing takes an error-string parameter. src/graphics/shader/recompiler/ShaderRecompiler.cpp:485…/ShaderRecompiler.cpp:615

Sharps, user data, and shader resource tables

This mechanism deserves special attention because it has no analogue in a normal graphics API.

A shader receives up to 64 dwords of user data in its first scalar registers, set by SET_SH_REG packets. Inside those dwords the game may place, in any arrangement it likes:

  • An inline V# / T# / S# descriptor — "sharp" in AMD's terminology: a buffer, image or sampler descriptor stored directly in registers.
  • A pointer to a table in memory holding descriptors, which the shader loads with s_load_dword. Tables may nest arbitrarily deep. This is the shader resource table, or SRT.

So to know which Vulkan image to bind, Kyty must evaluate the shader's own address arithmetic. Code follows typed IR values directly:

TranslateProgram() yields an immutable IR::ResourcePlan that the renderer's program cache keeps; on every draw IR::MaterializeResources() evaluates that plan against current user data and guest memory, producing a ResourceSnapshot (what to bind) and a ResourceSpecialization (what the SPIR-V may assume). The cache then looks up a permutation keyed on the specialization and, on a miss, calls CompileProgram() to emit it. The snapshot travels with the compiled program as a plain ShaderStageRuntime struct.

When the control flow cannot be structured

Some shaders have genuinely irreducible control flow — loops with multiple entry points, computed jumps through a code table. SPIR-V cannot express these directly. Rather than failing, the recompiler falls back to a dispatcher: the whole shader becomes one loop around a switch on a program-counter variable, with each basic block as a case. Slower, but universally correct.

BuildGraph() selects the fallback for irreducible graphs; a later Structurize() failure also falls back after restoring the unstructured graph. The reason and failing graph facts are logged rather than hidden.

Command submission

CommandScheduler now uses a growable command pool and a Vulkan timeline semaphore (MasterSemaphore). It reuses a command buffer when the GPU's known tick has passed that buffer's last submission, or allocates four more if none is free. Deferred destruction and descriptor-pool retirement are tied directly to timeline ticks; there is no fixed eight-buffer ring or per-buffer fence.

There is also a separate priority-operation thread. Some deferred work — a readback the guest is blocking on — cannot wait for the normal drain, so it runs on its own thread with its own tick.

…/renderer/commandScheduler.h…/renderer/masterSemaphore.h

What happens on a single draw

  1. Resolve render targets. Read the colour and depth register state, find or create images in the texture cache, transition their layouts.
  2. Fetch shaders. Hash the vertex and pixel shader code plus the derived input info into a ProgramKey; look it up; translate on a miss.
  3. Materialise resources. Re-run each shader's SRT plan against the current user data to get concrete textures and buffers, then find (or compile) the SPIR-V permutation for the resulting specialization.
  4. Upload dirty memory. For every bound resource, ask the memory tracker which pages the CPU touched and copy just those.
  5. Build the pipeline key. Pack the whole static state — viewport, scissor, depth test and blend colour are Vulkan dynamic state and stay out of it; look up or create the VkPipeline.
  6. Bind and record. Write descriptor sets, push constants, then vkCmdDrawIndexed or vkCmdDraw.

Vertex fetch has no fixed-function equivalent

On RDNA 2 there is no vertex-input state in hardware. Instead the driver compiles a small fetch shader that reads vertex attributes from buffers and leaves them in registers, and the real vertex shader is called with those registers already populated. Games may supply this fetch shader externally, or embed it in the vertex shader's prologue.

For the embedded case, DetectEmbeddedVertexFetch() analyses decoded instructions before IR construction and produces a Frontend::EmbeddedFetchPlan. That plan is supplied to TranslateProgram(), which emits the vertex-input behaviour directly.

Presentation, audio and input

The flip model

A PS5 game does not "present a frame." It registers a set of buffers with the video-out driver, renders into one, and then flips — asks the display hardware to scan out that buffer starting at the next vertical blank. The game learns the flip happened through an event queue.

Kyty reproduces the whole protocol:

  • VideoOutRegisterBuffers2 — the game hands over guest addresses and a tiling/format description. Kyty records them; images are created lazily by the texture cache.
  • VideoOutSubmitFlip — queued, not immediate. A flip submitted while another is pending must block, exactly as on hardware.
  • SubmitFlipFromGpu — the interesting case: a flip requested from inside the command stream, which must happen after the preceding draws complete. It becomes a Vulkan submission ordered by timeline semaphore.
  • VideoOutAddVblankEvent / VideoOutWaitVblank — a virtual vblank fires at the configured frequency (default 60 Hz, --vblank-frequency). Many engines pace their entire simulation off this, so the timing has to be steady even when rendering is slow.

Only at the very end does the guest's buffer get blitted into the SDL window's Vulkan swapchain image.

src/graphics/presentation/videoOut.cpp…/window/swapchain.cpp

Audio

Two distinct paths. sceAudioOut is straightforward mixing and output, running on its own thread and fed by the guest in fixed-size blocks. AJM is not: it models a hardware decode block, where the guest submits a batch of "jobs" describing input and output buffers and codec parameters. Kyty parses the job format and routes each to LibAtrac9 (Sony's ATRAC9 codec) or FFmpeg (AAC, MP3), behind one decoder interface (libs/ajm/decoder.h) that the Audiodec library shares. 12-channel AudioOut2 ports are downmixed to eight or two channels before SDL hears them.

Input

SDL2 supplies gamepad, keyboard, and mouse events on the main thread. libs/controller.cpp maps controllers onto the DualSense button mask and analogue axes; presentation/window/hostInput.cpp applies default PC controls or repeatable --keymap Control=Input bindings, including mouse buttons and mouse-to-right-stick mode. libPad.cpp reports the assembled state through scePadReadState, while PadSetVibration() forwards the two motor strengths to SDL_GameControllerRumble(). PadSetLightBar() and PadSetTriggerEffect() drive a real DualSense's light bar and adaptive triggers through SDL_GameControllerSetLED() and SDL_GameControllerSendEffect(); a DualShock 4 takes the same pad path, and the touchpad is emulated with the mouse.

A learning path through the source

Reading a 132,000-line emulator front to back does not work. Read it as a sequence of complete journeys instead — each one small, each one ending somewhere satisfying.

Six passes, in orderroughly increasing difficulty
1 · The whole boot, end to end2 hoursmain.cpp → emulator.cpp → RuntimeLinker::Execute(). Small files, and you will finish knowing the shape of the entire program. Do not detour into anything yet.
2 · One HLE function, all the way through1 hourPick something small in src/libs/ — libAppContent.cpp is a good size. Find its LIB_FUNC registration, then follow RuntimeLinker::Resolve() to see how the guest's relocation reaches it. This is the core HLE trick and it is only a few hundred lines.
3 · The loader in detailhalf a dayLoadProgramToMemory, ParseProgramDynamicInfo, Relocate, PatchProgram. Run with --game and read the log alongside — the loader prints every segment address, size and protection.
4 · Follow one draw calla dayTurn on --command-buffer-dump, run a 2D game, open the dump. Find an IT_DRAW_INDEX_AUTO packet. Then trace it: pm4Handlers.cpp → CommandProcessor::DrawIndexAuto → RenderExecutor::DrawAuto → renderDraw.cpp. This is the spine of the graphics stack.
5 · One shader, compileda dayTurn on --shader-log-direction File. Read the decoded RDNA 2 listing, then the CFG, then the IR, then look up the corresponding SPIR-V. Keep AMD's RDNA 2 ISA reference (document 70648) open — the README recommends it, and instruction semantics are not guessable.
6 · The coherency machineryhardestPageManager → MemoryTracker → TextureCache. Read tests/MemoryTrackerTests.cpp first: the tests state the invariants more clearly than the implementation does.

Habits worth adopting early

  • Run with logging on and read it. Kyty logs enormously and deliberately: every module load, every segment, every unresolved NID, every shader compile phase with timings. Most questions are answered faster by the log than by the source.
  • Treat EXIT_NOT_IMPLEMENTED as a map. Grep for it. Each one marks a case the author knew existed and chose not to handle — it is a catalogue of the emulator's frontier.
  • Read the tests as specification. For the shader compiler and the memory tracker, the tests are more precise than any comment.
  • Keep the guest/host boundary in mind at all times. When reading any function, ask: is this pointer a guest address or a host address? Is this code running on the guest's thread or the GPU thread? Most confusing bugs in emulators are a confusion about one of those two questions.

Glossary

The vocabulary that makes the code readable. Roughly in the order you will meet it.

HLEHigh-level emulation. Reimplementing what a console's system libraries do, in native code, instead of running the originals.
Guest / hostGuest = the emulated PS5 and its software. Host = the real PC, its OS and its GPU. Nearly every design decision in the codebase is about the boundary between them.
SELFSigned ELF. Sony's executable container: a small header and segment table wrapping an otherwise standard ELF64 file.
NIDThe 11-character encoded hash that names an exported symbol in place of a readable name. Written as hash#library#module.
PRX / moduleA PS5 shared library. Games ship some of their own alongside eboot.bin; Kyty preloads any it finds beside the executable.
TLS / TCBThread-local storage and its thread control block. Reached on PS5 through the fs segment, which is why the loader rewrites those instructions.
SysV ABIThe System V AMD64 calling convention, used by the PS5 (and by Linux and macOS). Differs from the Microsoft x64 convention in register assignment and stack layout.
Direct memoryPS5 physical memory, allocated by physical offset then mapped separately to a virtual address.
Flexible memoryPS5 paged memory from a fixed per-title budget declared in param.json.
AGCThe PS5's low-level graphics API — also called "Gen5" in this codebase. Its functions build PM4 packets rather than issuing draws.
PM4AMD's GPU command packet format. A stream of 32-bit dwords; type-3 packets carry an opcode and a body length.
Command processorThe GPU front end that reads PM4 and updates hardware registers. Kyty implements one in software: CommandProcessor.
DE / CEDrawing Engine and Constant Engine — two cooperating command engines, synchronised by counters, with the CE prefetching constant data ahead of the DE.
EOPEnd of pipe. An event that fires when all preceding GPU work has completed, typically writing a value to memory and raising an interrupt.
Tiling / swizzleThe non-linear memory layout GPUs use for textures. Converting to and from it is tile.cpp plus a family of compute shaders.
HTileA compressed metadata surface accompanying a depth buffer, storing per-tile depth ranges for fast rejection.
DCCDelta Colour Compression. Metadata alongside a render target that compresses colour writes.
RDNA 2The GPU architecture the PS5's graphics core is based on. Its shader instruction set is the recompiler's input language.
Wave / laneA wave is a group of 32 or 64 shader invocations executing in lockstep; each invocation is a lane. Branching is done by masking lanes off, not by jumping.
EXEC maskThe 64-bit register holding which lanes are currently active. Manipulating it is how RDNA 2 expresses control flow — and why converting to SPIR-V is hard.
SGPR / VGPRScalar and vector general-purpose registers. Scalar values are uniform across the wave; vector values are per lane.
Sharp (V# T# S#)A resource descriptor stored in registers or memory: V# buffer, T# image, S# sampler. The shader loads them itself at runtime.
SRTShader Resource Table. A possibly-nested table of descriptors in memory, reached from a pointer in user data. Kyty must statically work out how to walk it.
User dataUp to 64 dwords written into a shader's first scalar registers by SET_SH_REG packets — the only channel by which a draw passes parameters to its shaders.
Fetch shaderA small generated shader that reads vertex attributes into registers before the real vertex shader runs. RDNA 2 has no fixed-function vertex input.
SPIR-VVulkan's binary shader intermediate language, and the recompiler's output. Requires structured control flow.
FlipAsking the display to scan out a different buffer at the next vertical blank. The PS5's equivalent of "present."
VblankVertical blanking interval. Kyty generates a virtual one at a configurable rate; many engines pace themselves off it.

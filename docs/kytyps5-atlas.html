The whole machine, once through

Start here. Everything else on this page is one of these eight boxes opened up.

The thing to notice is that no step in that chain is a function call the emulator can intercept. The game writes command packets into memory it owns, then hands over a pointer. Everything after that is Kyty reading those packets and rebuilding the work in Vulkan.

01

The CPU — how guest code runs at all

The PS5's processor is an 8-core AMD Zen 2 running x86-64 — the same instruction set as your PC. That single fact reshapes the entire project.

So KytyPS5 is not a simulator that steps through the game. It is a host environment the game runs inside — closer in spirit to Wine than to Dolphin. The emulator only regains control when the game calls a function it provides, or when the hardware raises a fault.

01·2

The instructions match; the conventions do not

Machine code has no concept of a "function argument". Which register carries which parameter is a convention — and the PS5 and Windows disagree about almost all of it.

There is a second gap in the same family. Under System V a variadic function receives the count of vector registers used in al, which is why the generated import thunk begins with push rax, and why the guest's printf cannot simply be forwarded to the host's — guestPrintf.cpp is 25 KB reimplementing the format-string interpreter for exactly this reason.

01·3

Rewriting the guest's own instructions

Two instruction patterns in PS5 code cannot execute on Windows. With no recompiler in the pipeline, the loader rewrites the bytes in place — before the code is ever run.

You can watch this happen for real. Run any title, grep the log for Patch tls at addr, then look at those nine bytes in a debugger: the file on disk has 64 48 8B 04 25 00 00 00 00 and memory has E8 …. Seeing it once makes the whole mechanism concrete.

Faults are a control-flow mechanism

Because there is no code generation step, the emulator cannot instrument guest code. The CPU's own fault mechanism becomes the hook — and three of the handler's four branches are deliberate design.

02

Memory — carving up the address space

Console software hard-codes addresses and assumes allocations land in particular ranges. It also hands pointers to the GPU. So Kyty claims whole bands of the host address space up front and allocates inside them itself.

Three ways a game asks for memory, and Kyty models each separately: direct memory is a physical reservation that gets mapped as a second step; flexible memory comes from a fixed per-title budget; pooled memory is reserve-then-commit with a batch interface. On top sit sceKernelVirtualQuery — which forces real bookkeeping, since the guest can ask what protection, type, and name a range has — plus PRT apertures for sparse textures.

02·3

Keeping CPU and GPU copies in step

The hardest problem in the project. A console has unified memory, so games contain no synchronisation for this at all. On a PC, every shared resource is a copy that can go stale — and nothing tells the emulator when it does.

The code is unusually defensive about this, and the reason is worth internalising: a coherency bug produces corruption many frames after its cause, with no traceable link. So each invariant becomes an immediate crash instead — re-entering the tracker from inside an upload callback is a hard failure, and an invalidation that leaves GPU-owned pages behind aborts on the spot.

03·3

How a console call reaches emulator code

The single most important mechanism in the project, and it hinges on one pointer.

This is also the easiest place to contribute. Find a stubbed NID in a log, add a LIB_FUNC pointing at a function that logs its arguments and returns OK, and re-run — the stub message disappears and the game gets a little further. Two ways it silently fails: one wrong character in the NID string, or a LIB_VERSION whose library or module version does not match what the game imports.

04

Threads — who runs what

Three actors, three completely different jobs, and a separation that is required rather than stylistic.

Guest threads are real host threads, but with two pieces of state Kyty maintains itself: a guest stack allocated inside the guest bands, because guest code computes addresses relative to it and may hand them to the GPU; and a per-thread copy of every loaded module's TLS image, allocated lazily and freed through the game's own allocator if it installed one.

05

The GPU — packets in, pixels out

The game never calls a draw function. It builds raw command packets — the same binary format a real AMD command processor reads — and submits the buffer. So Kyty implements a command processor in software.

Beyond register writes and draws, a real command processor has mechanisms Kyty has to model too: two engines (drawing and constant) synchronised by counters, a 48 KB constant-RAM scratch area, end-of-pipe fences, indirect buffers that work like calls, predication that makes packets conditional, and blocking waits that suspend a submission rather than spinning.

src/graphics/guest_gpu/pm4.cpp:122…/pm4Handlers.cpp…/hardwareContext.h
05·2

Waves, lanes, and why shaders are hard

A GPU does not run one shader invocation at a time. It runs 32 or 64 in lockstep on one instruction stream — which means branching cannot work the way you expect.

src/graphics/shader/recompiler/cfg/ShaderCFG.cpp
05·3

RDNA 2 machine code becoming SPIR-V

26,000 lines of real compiler: decoder, control-flow graph, intermediate representation, dataflow analyses, code generator.

Structurisation is the stage most likely to fail, and failure is a supported outcome. When merge and continue blocks cannot be recovered — genuinely irreducible control flow, or a loop header holding an instruction whose own lowering emits control flow — the recompiler emits the whole shader as a dispatcher: one loop around a switch on a program-counter variable, each basic block a case. Slower, universally correct.

Finding the texture a shader wants

On RDNA 2 there are no texture slots. A shader holds its resource descriptors in registers, or loads them from memory itself — so the emulator has to evaluate the shader's own address arithmetic before the shader ever runs.

How a PlayStation 5 emulator works

KytyPS5 recreates parts of the PlayStation 5 environment on a PC. Its native execution path runs guest CPU code on the host CPU, supplies console services, and translates GPU work. Learn those boundaries step by step, then practice making a small, verified change.

The shape of it

Guest

A game module is an ELF no normal loader accepts. It imports functions by NID — short encoded ids, not names.

Kyty

The runtime linker resolves those ids against hand-written implementations, rewrites a few instructions, and jumps in.

Host

From there the code runs natively. There is no interpreter. The work is faking an OS and a GPU around it.

The GPU path has several additional translation stages. The game writes PM4 command packets into a ring buffer; a software command processor decodes them, turns accumulated register writes into Vulkan pipeline state, and translates compiled RDNA 2 shader binaries into SPIR-V. All the while CPU and GPU share memory each believes it owns, and coherency is held together by catching host page faults — with the guest convinced pages are 16 KB and the emulator's host tracking using 4 KB granularity; actual OS protection granularity is a separate constraint.

What you'll be able to do

  • 01Take a command-buffer dump from your own run and read it packet by packet — find the draw, and the state that set it up.
  • 02Open a game module and see exactly what the runtime linker sees: the Sony segments, the dynamic tags, the imports it can't resolve.
  • 03Verify a bounded HLE behavior with explicit output and error checks before making a compatibility claim.
  • 04Explain why a shader fell back to the dispatcher, and what would have to change for it not to.
  • 05Read a failing log and tell the difference between a cause and a symptom.

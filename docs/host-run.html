How the host runs a frame

The same frame, from the emulator's side. Every sce* call the guest made and every PM4 packet it wrote now has to be answered: HLE functions, the memory manager, page-fault coherency, the command processor, the shader recompiler, Vulkan, and the flip.

On the left, the calls arrive and the OS surface answers them (memory, threads, faults). In the middle, the GPU work is decoded and shaders are recompiled. On the right, Vulkan turns it into a real frame on your GPU. Step it with Prev/Next (or ← →), press Play, or click a box.

The four hard problems it solves

Being the operating system. Every sce* the guest calls has to do something real — allocate physical memory, create a thread, open a file. That is the HLE layer: dozens of hand-written modules that behave enough like the console's firmware for the game to keep going.

Keeping two views of memory in step. The guest thinks in 16 KB pages and shares memory with a GPU it believes it owns. The host works in 4 KB pages and has a separate GPU. The memory manager and the page-fault handler bridge both gaps — the fault is the notification channel that keeps CPU writes and GPU reads coherent.

Turning PM4 into Vulkan. The command processor decodes the guest's packets into register state; a draw with a new state or shader becomes a pipeline, compiling the RDNA 2 binary to SPIR-V on first sight (and caching it in two levels). Vulkan records and submits the result to your real GPU, and the flip model puts it on screen.

Surviving the differences. When the guest executes an instruction your CPU lacks, or touches memory it shouldn't, the exception handler catches it — emulating the instruction, handling the GPU fault, or printing the guest fault context and exiting.

Appendix · C8

A boot failure, diagnosed

Everything so far has been tools and vocabulary. This is the day you actually use them: a game that boots to a black screen and then crashes, walked from the command line to the fix — the same loop topic 19 turns into a habit.

Read

The scenario is real, the names are not. A title we'll call Neptune boots, stays on a black screen for a few seconds, and then the process dies. Everything below is what a diagnosis of that actually looks like.

The setup — turn the taps on

You never diagnose blind. Run once with everything the project has to say, pointed at files:

the first run
.\_Build\windows\install\kyty_emulator.exe --game "D:\Games\Neptune" `
  --printf-direction File --printf-output-file _kyty.txt `
  --command-buffer-dump true --shader-log-direction File

Three artifacts land on disk: _kyty.txt (every log line), the command-buffer dumps, and _Shaders/ (the shader compile trail). The --printf-direction and --shader-log-direction switches are the ones from topic 18; the playground tools are designed to read exactly these files. The screen is irrelevant now — the log is the evidence.

Step one — read the log in both directions

Open _kyty.txt. Top-down you see the boot story: modules loading, mounts happening, relocations resolving. Then, near the bottom, the unresolved imports — the loader logs every NID it could not bind, with the owning module:

from _kyty.txt — the work queue
[1][00:00:01.241] Loader::Programs:: ... : unresolved symbol rPo6tV8D9bM#B#A, lib = "Neptune_Game", mod = "Neptune_Game"
[1][00:00:01.244] Loader::Programs:: ... : unresolved symbol pT2fEBBpEJk#A#A, lib = "libScePad", mod = "libScePad"
[1][00:00:01.310] Loader::Programs:: ... : unresolved symbol 0GnN4QCgIfs#D#A, lib = "libSceVideoOut", mod = "libSceVideoOut"

Three habits, all learned earlier:

  • Bottom-up is for the crash; top-down is for the story. Unresolved imports are not errors yet — they become errors only if the game calls them. Each line is a candidate for topic 19.
  • The #B#A tail is the id encoding from the id encoder tool — module and library ids, not a readable name.
  • The whole log is droppable into the log triage tool, which groups these lines into "unresolved", "unimplemented", and "errors" buckets. That is the to-do list.

In Neptune's case the log ends not with unresolved imports but with the kyty_exception_handler: block. The black screen was the game waiting on a call that never returned; the crash is where it finally gave up.

Step two — the crash block, through the reader

Copy the crash block from _kyty.txt — from kyty_exception_handler: down through the Stack trace — into the crash-log reader. What comes back:

the crash, annotated
kyty_exception_handler: 0x00000009000A3B4C
exception module: D:\Games\Neptune\eboot.bin
exception: type=AccessViolation, av_type=Write, av_addr=0000000000000000, native_code=c0000005
regs: rax=0  rbx=... rcx=... rsp=...
Stack trace [thread = 1]:
[0] 00000009000A3B4C, off=00000000000A3B4C, eboot.bin
[1] 0000000900C01234, off=0000000000001234, libScePad.sprx

The discipline from topic C3, applied:

  • The symptom is the write to address 0. Something passed a null pointer into a function that wrote through it. The native code c0000005 is STATUS_ACCESS_VIOLATION — expected.
  • The cause is frame [1]. The crash happens in eboot.bin, but the caller is libScePad.sprx at offset 0x1234 — a pad library function. Neptune was reading a controller that isn't there, got a null state, and handed it onward.
  • Cross-check with the register table. rax = 0 is the giveaway: the value being written is a null. A register dump is only useful when you ask "which register was supposed to hold an address?"

Step three — confirm what the loader sees

The crash names libScePad.sprx. If the pad library resolved but behaves wrong, look at the module itself: drop eboot.bin or the .sprx into the module inspector. You expect the ET_SCE_* type and a PT_OS_DYNLIBDATA segment — the loader-only tags from topic 05. If those are present and the dynamic tags list includes DT_OS_NEEDED_MODULE for libScePad, the binding story is coherent and the bug is in the emulator's pad implementation, not the loading.

Step four — the instruction itself

From the crash block's code-32 bytes, you can decode the exact instruction that died. The RDNA2 decoder is for shaders, but the same idea applies here: feed the code-32 bytes to any x86 disassembler (or read them with Zydis, which is in the tree — topic C6) and confirm the operation is a store through a null base. That turns "access violation" into "this exact store wrote to a null pointer" — the difference between a symptom and a cause.

Step five — the fix loop

The pad library returned a null controller state where the game expected a valid one. The fix is exactly topic 19: find the pad padReadState-shaped function in src/libs/libPad.cpp, work out what it should return when no controller is attached, and return a zeroed-but-valid state instead of a null. The loop:

  1. Rebuild, re-run, confirm the kyty_exception_handler: line is gone.
  2. Confirm the game proceeds — the black screen clearing is the real test, not the absence of a crash.
  3. Re-run with the shader artifact reader on the _Shaders/ output once frames render — a black screen that doesn't crash is usually a shader problem, not a crash problem.

When it is not a crash

A persistent black screen with no crash block is a different animal, and it is worth listing its checklist because it comes up more often:

SymptomSuspectEvidence
Black screen, no crash, CPU idlea blocking HLE call never returnedthe log ends mid-import-resolution; PRINT_NAME trace stops at one function
Black screen, CPU busya draw is submitted but nothing renderscommand-buffer dump: feed the PM4 decoder; look for a draw with no render-target state (the Lab's pm4build shows the failure shape)
Black screen, first frame slow then nothinga shader fell back or failed to compile_Shaders/ + the shader reader: the SPIR-V is missing or the dispatcher fallback ran (topic 16)
Flicker then crash on frame Na resource lifetime bugthe crash trace names a texture/buffer address; the timeline story (topic C4) is the suspect
The whole method in one line

Run with the taps on → read the log top-down for the story and bottom-up for the crash → label each crash block (symptom = the address, cause = the stack trace) → confirm with the module and instruction tools → fix the caller → re-run until the black screen clears, then check the shaders. That is not debugging procedure; it is the entire course in one habit.

01

What an emulator is

An emulator makes one computer behave like another, so that software built for the second runs on the first. That is the whole idea. Everything else is engineering trade-offs about where you cut.

The simplest possible emulator

Imagine a toy machine with four registers and a handful of instructions. An emulator for it is a loop:

uint8_t memory[65536]{}; // load the toy program before executing
uint32_t reg[4]{};
uint16_t pc = 0;
auto fetch = [&]() { return memory[pc++]; }; // 16-bit PC wraps

for (;;) {
    switch (fetch()) {
        case 0x01: { // LOAD reg, little-endian imm32
            const uint8_t r = fetch();
            if (r >= 4) return; // invalid register
            uint32_t value = 0;
            for (unsigned byte = 0; byte < 4; ++byte)
                value |= uint32_t(fetch()) << (8 * byte);
            reg[r] = value;
            break;
        }
        case 0x02: { // ADD dst, src
            const uint8_t d = fetch(), s = fetch();
            if (d >= 4 || s >= 4) return;
            reg[d] += reg[s];
            break;
        }
        case 0xFF: return; // HALT
        default: return;  // invalid opcode
    }
}

This illustrates an interpreter: fetch an instruction, decode it, perform its operation, repeat. A complete implementation also defines invalid instructions, exceptions and every other part of the guest machine.

The loop adds decoding and dispatch work to every guest instruction. Its cost depends on the interpreter, host and workload; CPU clock rates alone cannot predict emulation speed. Caching translated code or executing compatible guest instructions natively can avoid much of that repeated work.

Execution strategies and HLE

Jargon · LLE versus HLE

Low-level emulation (LLE) reproduces lower-level hardware interfaces, often allowing original firmware or libraries to execute. It can preserve behavior that an HLE replacement omits, but neither accuracy nor speed follows from the label alone.

High-level emulation (HLE) replaces those libraries with reimplementations. It can avoid executing those system-library binaries, but each replacement must match the guest-visible contract. A missing function can fail immediately or fall back to a logging zero-return stub; silent incorrect results can cause failures much later. HLE does not by itself establish compatibility.

KytyPS5 primarily replaces system services with HLE. Its README says no external low-level emulation modules are required. The loader can still execute a game-supplied /app0/sce_module/libc.prx; “HLE” does not mean every instruction outside the main executable is replaced.

What an emulator must actually reproduce

A CPU is only one of the things a program depends on. To run an unmodified console game you must reproduce all of:

  1. The instruction set — so the code executes at all.
  2. The calling convention — so a function's arguments arrive where it expects them.
  3. The memory layout — so pointers, allocations and alignment assumptions hold.
  4. The operating system's services — threads, files, memory, timers, networking, audio, input.
  5. The GPU — including its command format, its register set, its memory layouts and its shader instruction set.
  6. The timing model — vertical blank, frame pacing, audio clocks. Games are full of code that assumes 60 Hz.

Most ordinary guest CPU instructions execute directly in a compatible x86-64 environment. Targeted instruction compatibility is still necessary; the remaining responsibilities account for most of this project.

03

Why there is no CPU emulator

KytyPS5 has no general guest-CPU interpreter or dynamic binary translator. It does generate ABI stubs and instruction trampolines, and it has a separate GPU shader compiler. This chapter explains how native guest-CPU execution fits those pieces together.

The instruction sets are the same

A PS5 game contains x86-64 machine code. In a compatible x86-64 host environment, most instructions can execute directly. Kyty handles specific instruction-feature gaps separately. The emulator:

  1. Allocates memory at the address the executable wants,
  2. Copies the code segments into it,
  3. Marks those pages executable,
  4. Sets up a stack and jumps to the entry point.

From that instruction onwards the CPU executes ordinary game instructions directly. The emulator is not "in the loop" at all — it only regains control when the game calls a function the emulator provides, or when the hardware raises a fault.

The mental model that matters

KytyPS5 is not a simulator that steps through the game. It is a host environment that the game runs inside. It is closer in spirit to Wine — which runs Windows programs on Linux — than to an emulator like Dolphin. Everything the emulator does is reactive: it responds to calls, to page faults, and to command buffers.

What that buys, and what it costs

Prerequisite: x86-64 and calling conventions

The instruction sets match; the conventions do not. This chapter is the minimum x86-64 you need, and then the specific mismatch that shapes a surprising amount of KytyPS5.

The registers

x86-64 has sixteen 64-bit general-purpose registers. Their names are historical and inconsistent, which is confusing at first and then stops mattering:

rax rbx rcx rdx        the original four, extended to 64-bit
rsi rdi                "source index" / "destination index"
rbp rsp                frame pointer / stack pointer
r8 r9 r10 r11          added with x86-64
r12 r13 r14 r15

xmm0 … xmm15           128-bit vector registers, used for float arguments too
rip                    instruction pointer (not directly writable)
rflags                 condition flags

Plus segment registers, a leftover from 16-bit days. In 64-bit mode most are ignored, but two survive with a specific job: fs and gs provide a per-thread base address, used to reach thread-local storage. Remember fs — it comes back in chapter 16 and causes real trouble.

What a calling convention is

Machine code has no concept of a "function argument." When you write f(a, b), the compiler must decide: which register or stack slot does a go in? Who cleans up the stack? Which registers may f destroy? A calling convention (or ABI, application binary interface) is the agreed answer.

Two conventions matter here, and they disagree about almost everything:

Where do the arguments go?change the count
System V AMD64 — used by the PS5, Linux, macOS
Microsoft x64 — used by Windows

System V passes six integer arguments in registers; Microsoft passes four, and requires the caller to reserve 32 bytes of "shadow space" on the stack even when all arguments fit in registers. The register order is different too — rcx is the fourth argument under System V and the first under Microsoft.

They also differ on which registers a function must preserve. Under System V, rbx rbp r12–r15 are callee-saved. Under Microsoft, that list additionally includes rsi rdi and all 128 bits of xmm6–xmm15 (the upper YMM/ZMM portions remain volatile). A function compiled for one convention and called by the other will silently corrupt registers the caller expected to survive.

How KytyPS5 bridges it

Clang lets you set the convention per function with an attribute. Kyty defines two macros and uses them everywhere the boundary is crossed:

src/common/abi.h
#define KYTY_MS_ABI   __attribute__((ms_abi))
#define KYTY_SYSV_ABI __attribute__((sysv_abi))

Any function the guest can call is marked KYTY_SYSV_ABI. The compiler then emits a System V prologue for that one function, while the rest of the emulator is compiled with the platform's native convention:

int KYTY_SYSV_ABI ContentExportInit2(const ContentExportInitParam2* init_param) {
    PRINT_NAME();
    if (init_param == nullptr) return CONTENT_EXPORT_ERROR_INVALID_PARAM;
    ...
}

The reverse direction exists too. When the emulator generates machine code that guest code will call — the TLS stubs of chapter 16 — that stub must switch back to the Microsoft convention before calling into C++. You can read the switch happening by hand in Jit::SafeCall:

Why the build refuses MSVC

Microsoft's compiler has no sysv_abi attribute. There is no way to write this code in MSVC, so the root CMakeLists.txt rejects cl.exe and the supported Windows build uses clang-cl. The POSIX branches also recognise GCC, although the documented and CI builds use Clang.

One more x86-64 detail: variadic functions

System V variadic calls carry the vector-register argument count in al. The current diagnostic import stub does not forward variadic calls; guestPrintf.cpp interprets the guest argument list explicitly instead of passing it to a host vprintf.

It is also why Kyty cannot simply forward a guest printf to the host's vprintf: the argument list layout differs. src/libs/guestPrintf.cpp implements the guest format-string interpreter and argument decoding for exactly this reason.

Prerequisite: virtual memory and page protection

Page protection is not a side topic in this project — it is the mechanism by which the emulator detects that the game has touched something the GPU cares about. You need to understand it properly.

Addresses are lies

When a program reads address 0x900001000, that is a virtual address. The CPU's memory management unit translates it, through page tables the OS maintains, into a physical address in RAM. The translation happens per page — a fixed-size block, 4 KB on PC, 16 KB on PS5.

Each page table entry carries permission bits: readable, writable, executable. If a program accesses a page in a way the bits forbid, the CPU raises a fault. The OS delivers it to the process as an exception (Windows) or a signal (Linux, macOS).

Jargon · reserve versus commit

Reserving address space claims a range of virtual addresses so nothing else can use them, without allocating any physical memory. Committing backs part of that range with real memory.

This split is why an emulator can claim a terabyte of address space up front (see the memory map below) while using only a few gigabytes of RAM. Kyty reserves entire bands and hands out committed pieces from inside them.

The three things Kyty does with protection

1 · Enforce the guest's own protectionskytyWhen the game calls sceKernelMprotect, Kyty applies the equivalent host protection so that a genuine guest bug still faults the way it would on console.
2 · Detect CPU writes to GPU datakytyMemory the GPU has cached as a Vulkan image is deliberately write-protected. When the game writes to it, the fault tells the renderer its copy is stale. The fault is the notification.
3 · Commit reserved ranges lazilykytyEligible faults in the guest backing ranges can commit missing backing. A reserved address alone does not make an access valid; guest mappings, permissions and ownership still matter.

All three funnel into one function — the exception handler installed by the loader — which is why chapter 18 exists.

The page-size mismatch

The PS5 uses 16 KB pages; PCs use 4 KB. Kyty's guest allocator works in 0x4000-byte units:

src/loader/runtimeLinker.cpp
constexpr uint64_t GUEST_PAGE_SIZE = 0x4000;
program->base_size_aligned = AlignUp(program->base_size, GUEST_PAGE_SIZE);

One 16 KB guest page spans four 4 KB host pages. Guest VM alignment and renderer tracking are separate: TRACKER_PAGE_SIZE is 4 KB, so a tracking fault does not inherently dirty the entire 16 KB guest page. Host protection calls accept ranges and can cover several pages in one call.

The address map Kyty imposes

Kyty does not let the host OS choose where things go. It divides the address space into bands and enforces them:

Why bands, not just "ask the OS"

Console software hard-codes addresses and assumes allocations land in particular ranges. It also passes pointers to the GPU, which in Kyty means those pointers must be distinguishable from emulator pointers. Fixing the bands makes both problems tractable: use the actual range bounds and loaded-segment metadata to classify an address. A hexadecimal prefix alone does not prove that a value is guest code, heap data or a host pointer.

Prerequisite: ELF and dynamic linking

A game is a file. Something has to turn that file into a running program. On Linux that job belongs to ld.so; in KytyPS5 it belongs to RuntimeLinker. To read that code you need to know what a dynamic linker does.

The ELF layout

ELF — Executable and Linkable Format — is the Unix executable format, and the PS5 uses it. An ELF file has two overlapping views:

ViewDescribed byUsed by
Sections (.text, .data, .rodata…)Section headersThe linker at build time. Often stripped from shipped binaries.
Segments (PT_LOAD, PT_DYNAMIC, PT_TLS…)Program headersThe loader at run time. This is the view Kyty cares about.

A program header entry says: "take p_filesz bytes at file offset p_offset, place them at virtual address p_vaddr, zero-fill up to p_memsz, and apply these permissions." Loading is essentially a loop over those entries.

Why relocation exists

A shared library does not know where it will be loaded. It is compiled position-independently, and every absolute address inside it is left as a placeholder. The loader must go back and fix them. Each fix is a relocation: a record saying "at offset X, write value Y."

Jargon · GOT and PLT

The Global Offset Table is an array of pointers. Instead of embedding an absolute address in code, the compiler emits "load the pointer from GOT slot 12, then use it." The loader fills the GOT, so the code itself never needs patching.

The Procedure Linkage Table is the same idea for calls. A call to an external function jumps to a small PLT stub, which jumps to whatever address the GOT holds.

This is the hook KytyPS5 uses. When the loader writes the address of its own C++ function into a GOT slot, every subsequent guest call to that "console function" lands in the emulator instead. No patching of the game's code is needed.

Symbols, and why the PS5's are unreadable

Normally a dynamic symbol has a name: printf, malloc. PS5 modules instead export NIDs — an 11-character encoding of a hash of the original name — qualified by the library and module they belong to:

b4fpgH5ZXxQ#Graphics5Driver#Graphics5Driver
└─ symbol ─┘ └─── library ───┘ └──── module ────┘

Kyty stores its HLE implementations under the same key, so resolution is a dictionary lookup. You will meet the exact mechanism in chapters 15 and 22.

Thread-local storage in one paragraph

A variable declared thread_local needs a different copy per thread. The usual implementation gives each thread a block of memory and a pointer to it, reachable through a segment register — fs on x86-64 Linux and FreeBSD. Code that reads a thread-local reads fs:[offset].

On x86-64 Windows the host TEB uses gs; a guest fs access does not address the guest TLS block. Chapter 16 is entirely about the fix.

Prerequisite: how a GPU actually draws

Half of KytyPS5 is graphics, and the graphics code assumes you know how the hardware works — not how an API looks. This chapter covers the hardware model.

The pipeline

To draw a triangle, a GPU runs a fixed sequence of stages. Some are programmable (you supply a shader), some are fixed-function (configured by registers):

Input assemblyfixedRead the index buffer, group vertices into primitives (triangles, lines, points).
↓
Vertex shaderprogrammableRuns once per vertex. Reads attributes, outputs a clip-space position plus arbitrary interpolated values.
↓
RasterisationfixedConvert each triangle into the set of pixels it covers. Interpolate the vertex outputs across that area.
↓
Pixel (fragment) shaderprogrammableRuns once per covered pixel. Samples textures, computes lighting, outputs colour — and optionally depth.
↓
Depth / stencil test, blendingfixedReject hidden pixels, combine the new colour with what is already in the render target.

Separately, compute shaders bypass all of this: they run a grid of threads doing arbitrary work, used for physics, culling, post-processing and — in Kyty — for detiling textures.

How shaders actually execute: waves and lanes

This is the part that trips people up, and it is essential for chapter 30.

A GPU does not run one shader invocation at a time. It runs a wave — 32 or 64 invocations — in lockstep on one instruction stream. Each invocation is a lane. One instruction, executed simultaneously for all lanes on their own data.

So what happens at an if? Lanes can take different logical paths, but the wave shares an instruction stream. Instead the hardware keeps an execution mask: a 64-bit register where bit n enables lane n. Branching is implemented by masking:

          // if (x > 0) { A } else { B }
v_cmp_gt_f32  vcc, v0, 0      compare in every lane → 64-bit result in vcc
s_and_saveexec_b64  s[0:1], vcc   enable only lanes where the test passed
          … vector code for A — masked lanes do not update results …
s_andn2_b64   exec, s[0:1], exec  flip to the other lanes
          … code for B …
s_mov_b64     exec, s[0:1]        restore

In this example both vector instruction sequences are visited and disabled lanes do not update their vector results. Scalar instructions are wave-wide, and scalar branches can skip blocks; EXEC masking is not a universal rule for every instruction. This is why GPU code is fast when threads agree and slow when they diverge — and, more importantly for us, why GPU control flow is data manipulation rather than program structure. Recovering structure from it is the hardest job the shader recompiler has.

Jargon · scalar versus vector registers

RDNA 2 has two register files. VGPRs (vector registers) hold a different value per lane — a pixel's colour, a vertex's position. SGPRs (scalar registers) hold one value shared by the whole wave — a loop counter, a base address, a resource descriptor.

Image and buffer instructions consume resource descriptors through scalar registers, but shaders can load those descriptors from memory using runtime-selected addresses. Kyty must trace that dataflow and, where supported, discover a bounded set of compatible descriptor candidates.

Descriptors: how a shader reaches a texture

In a PC API you call BindTexture(slot, texture). On RDNA 2 there are no slots. A texture is described by a descriptor — a packed block of bits holding its address, format, size, tiling and swizzle — and the shader simply has that block in its registers, or loads it from memory itself.

Tiling: textures are not stored in rows

A linear image stores pixel (x, y) at base + y*pitch + x*bpp. GPUs do not do this, because a shader sampling a texture reads a 2D neighbourhood, and a linear layout puts vertically adjacent pixels far apart in memory.

Instead pixels are interleaved into small blocks so that a 2D neighbourhood lands in one cache line. AMD has several schemes — 256 B, 4 KB, 64 KB, plus special layouts for render targets, depth buffers and partially-resident textures — each with its own swizzle function and alignment rules that vary with bytes-per-pixel and mip level.

Guest memory holds tiled data. Vulkan wants either linear data or its own opaque layout. Converting between them is chapter 29.

Why "explicit" matters here

In OpenGL the driver guessed what you meant, tracked state changes and re-compiled shaders behind your back. Vulkan removes all of that: you declare everything up front and manage synchronisation yourself.

For an emulator this is exactly right, because the guest has already declared everything — the PM4 register state is a complete pipeline description. Kyty's job is translation, not inference. The awkward part is the reverse: Vulkan bakes state into immutable pipeline objects, whereas the guest changes registers freely, so Kyty must detect which changes actually require a new pipeline. That is what the pipeline cache key is for.

SPIR-V, and why it is stricter than machine code

Vulkan does not accept GLSL or HLSL. It accepts SPIR-V: a binary intermediate language of 32-bit words. Every value has a declared type, every capability used must be requested, and — critically — control flow must be structured.

Structured means: every conditional branch declares in advance where its two paths reconverge (the merge block), and every loop declares both its merge block and its continue target. In SPIR-V assembly:

OpSelectionMerge %merge None      "these branches rejoin at %merge"
OpBranchConditional %cond %then %else
%then = OpLabel
  ...
  OpBranch %merge
%else = OpLabel
  ...
  OpBranch %merge
%merge = OpLabel

Compare that with the RDNA 2 snippet in chapter 7, which had no merge point at all — just mask manipulation and fall-through. Reconstructing the declarations SPIR-V demands, from code that never had them, is the single hardest pass in the recompiler, and it is allowed to fail: there is a documented fallback for shaders whose control flow cannot be structured.

A worked mapping

Multiply is easy. The work is in the thousand cases that are not: packed 16-bit maths, saturating conversions, cross-lane shuffles, image sampling with a dozen modifier bits, buffer loads that need bounds checking SPIR-V does not provide for free.

Kyty has no dependency-injection framework or service locator. Current code uses a singleton template where global identity is needed, plus a small explicit lifecycle stack that guarantees reverse-order normal or emergency teardown.

The subsystem contract

A managed component exposes a lightweight Lifecycle type. It always names an initialize callback and may provide normal and emergency shutdown callbacks:

    static constexpr const char* name       = "Graphics";

The main thread becomes the window and input loop; the game gets a spawned thread. This is required — macOS and Windows both insist that window creation and event pumping happen on the process's first thread — and it has a useful side effect: a hung game does not freeze the window.

And then the guest thread

src/loader/runtimeLinker.cpp
void RuntimeLinker::Execute(const std::filesystem::path& game_patch) {
    Libs::LibKernel::PthreadInitSelfForMainThread();
    auto* main_stack_top = Libs::LibKernel::PthreadCreateMainGuestStack();

#if KYTY_PLATFORM == KYTY_PLATFORM_WINDOWS
    // Guest code has no Windows stack probes and may jump over the guard page.
    size_t expanded_size = 0;
    while (expanded_size < static_cast<size_t>(768) * 1024) {
        sys_dbg_stack_info_t stack {};
        SysStackUsage(stack);
        *reinterpret_cast<uint32_t*>(stack.guard_addr) = 0;   // force commit
        expanded_size += stack.guard_size;
    }
#endif

    const auto libc_path = Libs::LibKernel::FileSystem::GetRealFilename("/app0/sce_module/libc.prx");
    auto* libc = Common::File::IsFileExisting(libc_path) ? LoadProgram(libc_path) : nullptr;
    RelocateAll();                 // resolve every import in every module

    if (!game_patch.empty()) GamePatch::Apply(game_patch, m_programs.front());
    if (libc != nullptr && libc->dynamic_info->init_vaddr != 0) {
        StartModule(libc, 0, nullptr, nullptr);
    }

    if (auto entry = GetEntry(); entry != 0) {
        auto* params = reinterpret_cast<EntryParams*>(
            (reinterpret_cast<uintptr_t>(main_stack_top) - 0x100u) & ~static_cast<uintptr_t>(0x0f));
        std::memset(params, 0, sizeof(EntryParams));
        params->argc    = 1;
        params->argv[0] = "KytyEmu";
        RunEntry(entry, params, ProgramExitHandler, ...);   // never returns normally
    }
}
Why 768 KB of stack is touched on purpose

Windows commits thread stacks lazily with a guard page: touching it faults, the OS commits another page and moves the guard down. This only works if code touches the stack in order, which is why MSVC emits __chkstk probes for large stack frames.

PS5 code, compiled for FreeBSD, has no such probes. A function with a large local array can write past the guard page, and Windows will then treat that as a real stack overflow and terminate the process. Module initialisers also run on the host stack before the guest stack is in use.

So Kyty walks the guard page down 768 KB by hand before any guest code runs, forcing the whole region to commit up front.

Once RunEntry jumps, the CPU is executing the game. Everything the emulator does from then on is reactive: it responds to function calls, to page faults, and to submitted command buffers.

Directories and ZArchive content

Three details worth extracting:

  • Patch before protect. The rewriting in chapter 16 needs write access, and the instruction cache flush must happen after the bytes change. Reversing the order would either fault or execute stale instructions.
  • skip_protect exists because some PS5 executables declare PT_LOAD segments with no access flags at all. Applying NoAccess literally would make them unreadable; the loader leaves them mapped instead.
  • The TLS image is a template. PT_TLS describes the initial contents; each thread gets its own copy, allocated lazily by TlsGetAddr.

Relocation and NID resolution

This is the join between guest and emulator. Understanding it makes the entire HLE design obvious.

What a relocation record contains

The HLE database is searched first. That is the whole trick: if Kyty implements a function, the guest gets Kyty's address even when a real module also exports it.

Eager relocation and dynamic-module lifetimes

RelocateRecord() resolves both relocation tables eagerly. Program::rela_bits records successful bindings, so loading another module retries unresolved imports without overwriting existing guest-modified slots. RelocateProgram() refreshes all loaded importers after a dynamic load. Guest PLT/GOT records still exist, but the emulator's former lazy-PLT setup and DynamicInfo::pltgot_vaddr field have been removed.

Explicit module loads increment Program::load_count; the final explicit unload releases the module. Before unmapping, UnloadProgram() identifies imports bound to that module's exact exported address, clears their resolved bits and relocates them again. Matching only a NID could unlink a different provider, so SymbolDatabase::FindByNid() also accepts an address filter.

Unresolved function imports still receive diagnostic thunks; unresolved objects point at invalid memory. A thunk is the fallback for an unresolved import, not the ordinary mechanism for deferring all symbol binding until first call.

Patching guest instructions

Two instruction patterns in PS5 code cannot execute on Windows. Since there is no recompiler to fix them during translation, the loader rewrites the bytes in place before the code is ever run.

Problem 1 — thread-local storage through fs

PS5 code reads its thread control block with a single instruction:

64 48 8B 04 25 00 00 00 00     mov rax, qword ptr fs:[0]

On x86-64 Windows the host TEB is addressed through gs. The guest’s fs:[0] assumption does not provide its TCB on the host, so the loader redirects the recognized access to a guest TLS helper.

The fix replaces those exact nine bytes with a call to a generated stub, then moves the result into whatever register the original targeted:

src/loader/runtimeLinker.cpp
const uint8_t tls_pattern[5] = {0x64, 0x48, 0x8B, 0x00, 0x25};

for (auto* ptr = start_ptr; ptr <= end_ptr; ptr++) {
    auto*  inst_ptr     = ptr;
    size_t prefix_count = 0;
    // compilers pad this sequence with up to three 0x66 prefixes
    while (prefix_count < 3 && inst_ptr < start_ptr + size && *inst_ptr == 0x66) {
        inst_ptr++; prefix_count++;
    }

    const uint8_t modrm = inst_ptr[3];
    if (memcmp(inst_ptr, tls_pattern, 3) == 0 && (modrm & 0xc7u) == 0x04u &&
        inst_ptr[4] == tls_pattern[4] &&
        *reinterpret_cast<const uint32_t*>(inst_ptr + 5) == 0) {

        const auto reg = (modrm >> 3u) & 7u;      // which register was the destination
        EXIT_NOT_IMPLEMENTED(reg == 4u);          // rsp would be nonsense

        auto* code = new (ptr) Jit::Call9;
        code->SetFunc(reg == 0 ? program->tls.handler_vaddr
                               : program->tls.handler_vaddr + Jit::TlsRegStub::GetOffset(reg));
        ...
    }
}

Jit::Call9 is exactly nine bytes, so the replacement is size-neutral and no addresses shift:

src/loader/jit.h
struct Call9 {
    void SetFunc(Handler func) { // compute a rip-relative displacement }
    static uint64_t GetSize() { return 9; }

    // call func      E8 xx xx xx xx
    // mov  rax,rax   48 89 C0
    // nop            90
    uint8_t code[9] = {0xE8, 0, 0, 0, 0, 0x48, 0x89, 0xC0, 0x90};
};

The mov rax,rax byte is rewritten by SetOutputReg so the value lands in the register the original instruction wanted. For registers other than rax the stub jumps to a per-register variant at a fixed offset (TlsRegStub::GetOffset(reg)), each of which does call handler; mov <reg>, rax.

Why this is expensive but acceptable

A single instruction has become a call plus register spills. Thread-local reads are common but not usually in the hottest loops, and the cached fast path keeps the handler short. The alternative — a full recompiler — costs vastly more.

Problem 2 — the stack canary

Compiler stack-protector code stores a guard value through fs:[0x28]. With an unsuitable FS base this can fault, including at address 0x28 when that base is zero. The loader recognizes this store pattern:

src/loader/runtimeLinker.cpp
const uint8_t fs_store_pattern[8] = {0x64, 0xc7, 0x04, 0x25, 0x28, 0x00, 0x00, 0x00};

for (auto* ptr = start_ptr; ptr <= end_ptr; ptr++) {
    if (memcmp(ptr, fs_store_pattern, sizeof(fs_store_pattern)) == 0) {
        LOGF("Patch fs:[0x28] store at addr: [%016" PRIx64 "]\n", (uint64_t)ptr);

        // recognise the specific "canary failed → ud2" epilogue
        if (ptr + 16 < start_ptr + size && ptr[12] == 0xcd && ptr[13] == 0x45 &&
            ptr[14] == 0x90 && ptr[15] == 0x0f && ptr[16] == 0x0b) {
            ptr[0] = 0x5d;                    // pop rbp
            ptr[1] = 0xc3;                    // ret
            std::memset(ptr + 2, 0x90, 15);   // nop the rest
        } else {
            std::memset(ptr, 0x90, 12);       // just nop the store
        }
    }
}

This is a compatibility rewrite of a recognized instruction pattern. It changes the guest’s stack-protector behavior; it is not a general implementation of the guest TLS or stack-canary contract.

Optional AMD patches and host instruction gaps

--amd-cpu enables the shared guestInstructionPatcher.cpp path on Windows, Linux and x86-64 macOS. PatchGuestInstructions(..., protect_memory, emulate_amd, host_features) uses function boundaries from .eh_frame and registered trampoline space. It patches supported VRSQRTPS forms and fills host-feature gaps for EXTRQ, INSERTQ, RDPID and CLWB, preferring native trampolines with safe trap fallbacks. Windows red-zone protection is controlled separately by --redzone.

The patch result records per-family counts for reciprocal square root, EXTRQ, INSERTQ, RDPID and CLWB, distinguishing native patches from trap fallback. Host features decide which compatibility path is needed; x86-64 macOS signal handling also preserves the SSE4a context. Native TLS keeps fiber context valid across host-thread migration, and fiber ownership preserves small guest stacks.

How to see this yourself

Run any title and grep the log for Patch tls at addr. Take one of those addresses into a debugger and look at the nine bytes: you will find E8 … where the ELF file on disk has 64 48 8B 04 25 00 00 00 00. Seeing that once makes the whole mechanism concrete in a way no description does.

Unresolved imports and generated thunks

Real games import thousands of functions Kyty has never implemented. The strategy for handling that is the difference between an emulator that boots nothing and one that boots most things.

The design decision

Three options exist when a symbol will not resolve:

OptionResult
Abort at load timeAlmost nothing boots. Games import far more than they call — an unused code path drags in an entire library.
Write null into the GOTThe game crashes on the first call with no context. The log says nothing useful.
Write a generated stubOnly code paths actually taken can break; the stub logs which NID is missing and returns zero. This is what Kyty does.

The thunk, byte by byte

AllocateUnresolvedImportThunk() emits a 34-byte diagnostic stub. It calls UnresolvedImportStub(record_id), which logs the missing import (subject to the shared 1,024-call log limit) and returns zero. It does not preserve arguments for a lazy retry or tail-call a newly found target.

48 BF <record_id:8 bytes>  mov rdi, record_id
48 B8 <stub:8 bytes>       mov rax, UnresolvedImportStub
FF D0                      call rax          // RAX receives zero
48 83 C4 08                add rsp, 8
0F 57 C0                   xorps xmm0, xmm0  // zero floating return register too

A later dynamic module load retries unresolved relocation slots eagerly through RelocateAll(). The thunk itself only diagnoses an unresolved call. Returning zero can let a game continue while still hiding missing behavior, so a title that boots with stubs is not evidence that those APIs are implemented.

Exceptions as control flow

Because guest code normally runs natively, Kyty does not instrument every memory access. The CPU's own fault mechanism becomes the emulator's primary hook — two of the handler's three branches are load-bearing, not diagnostic.

The handler

src/loader/runtimeLinker.cpp
static bool KytyExceptionHandler(const Common::HostException::ExceptionInfo& exception_info) {
    const auto* info = &exception_info;

    // 1 — an instruction this CPU does not have

        Loader::X64InstructionEmulator::TryEmulate(info->native_context)) {
        return true;

    if (info->type == ExceptionType::AccessViolation) {

Reservations are committed explicitly. A fault in reserved-but-uncommitted memory is a real bug and falls through to the dump.

Returning true means "handled, resume execution." The guest never learns anything happened.

Branch 1 — emulating missing instructions

The PS5's Zen 2 supports instructions your CPU might not, notably the SHA extensions. When one executes, the CPU raises an illegal-instruction fault, and X64InstructionEmulator decodes the bytes at the fault address, performs the operation in software against the saved register context, and advances the instruction pointer past it.

src/loader/x64InstructionEmulator.cpp — the SHA1 message schedule, in software
static void Sha1Msg1(XmmWords& dest, const XmmWords& src2) {
    const uint32_t w0 = dest.w[3];  const uint32_t w1 = dest.w[2];
    const uint32_t w2 = dest.w[1];  const uint32_t w3 = dest.w[0];
    const uint32_t w4 = src2.w[3];  const uint32_t w5 = src2.w[2];
    dest.w[3] = w2 ^ w0;   dest.w[2] = w3 ^ w1;
    dest.w[1] = w4 ^ w2;   dest.w[0] = w5 ^ w3;
}

It is slow — a fault plus a software emulation per instruction — but these appear in checksum and hashing routines rather than in hot loops, and the alternative is not running at all.

Branch 2 — the GPU fault, and why it is the design

This is the most important branch in the emulator. Memory the GPU has cached as a Vulkan image or buffer is deliberately write-protected. When the game writes to it:

Branch 3 — the crash dump

When nothing handles the fault, the handler prints a --- Guest fault context --- block — everything it can read without faulting again — and then exits through EXIT:

  • The guest thread name from the pthread layer (or (host thread) if the fault was not on a guest thread) — which identifies the thread, not the executing module; use the faulting PC to locate the code.
  • All sixteen general-purpose registers, four per line, as rax=….
  • 96 bytes of code around the fault address — pc-48 .. pc+48, the faulting byte at offset 48 — probed with IsReadableRange first so the dump does not itself fault.
  • 32 stack qwords read from rsp, again only if readable.
  • The final Unhandled host exception: type=… code=… pc=… access=… address=… line: the exception type, the native code, the program counter, the access kind and the address that was touched.

This fault path prints guest context rather than a host stack walk. The guest frame-pointer walker is RuntimeLinker::StackTrace(), which prints Stack trace [thread = N]: followed by one [i] address, off=…, module line per frame, resolved against the loaded modules; the libc abort path calls it. Accepting a frame only when the return address lands inside a loaded module's segments is precisely what fixing the module layout in chapter 14 buys.

Four allocation entry points serve different purposes, and choosing the wrong one is a real bug class:

The separate extended-memory arena

Ordinary guest mappings keep their existing low address bands. Extended allocations use a separate 512 GiB virtual arena at 0x080000000000, an 8 TiB base, described by kExtendedMemoryBase and kExtendedMemorySize in kernel/memory.h. Reserving that address range does not allocate 512 GiB of physical RAM. Extended requests and ordinary mapping searches have separate allocation rules.

GPU tracking accepts the low 1 TiB region and that explicit extended interval; the space between them is not a valid resource range. Sparse image tracking covers 44-bit addresses. Dense buffer/BDA tables pack the low and extended intervals together through BufferCache::PageIndex() (guest address to packed page index) and GuestAddress() (packed byte offset to guest address), avoiding tables for the entire gap.

Automatic backing is recycled through physical-allocation ownership. Reserved mappings are published only after backing commit succeeds, and partial POSIX unmaps preserve still-live mappings. These are allocation/alias invariants tested by VirtualMemoryAllocationTests.cpp. Host primitives are declared directly in common/virtualMemory.h and implemented by sysWindowsVirtual.cpp / sysLinuxVirtual.cpp.

Threads and thread-local storage

Short sleeps block too

KernelUsleep() and KernelNanosleep() use signal-polling sleep helpers. Nonzero short waits use blocking waits with signal polling. Windows uses its high-resolution waitable timer path; POSIX uses an absolute monotonic deadline that survives signal interruptions. Zero-duration requests still have their explicit signal-dispatch behavior.

Guest threads are real host threads — but with two pieces of state Kyty has to maintain itself, and a set of FreeBSD semantics that do not come free.

What pthread.cpp implements

Guest stacks

A guest thread cannot simply use the host thread's stack. Guest code computes addresses relative to its own stack, and those addresses may be handed to the GPU or stored in structures Kyty inspects — so they must lie inside the guest address bands:

Why lifetime is the hard part

A queue can be destroyed while another thread is blocked in KernelWaitEqueue, or while the graphics thread is part-way through delivering an event into it. Kyty pins queues with a shared pointer for the duration of any operation:

using KernelEqueueRef = std::shared_ptr<KernelEqueuePrivate>;
[[nodiscard]] KernelEqueueRef KernelPinEqueue(KernelEqueue eq);

Each attached filter also carries a std::shared_ptr<void> owner and a delete_event_func, so a source can keep its own state alive exactly as long as the event exists. tests/EventQueueLifetimeTests.cpp exercises event lifetime and ownership.

KernelAddTimerEvent() registers periodic microsecond timers using KERNEL_EVFILT_TIMER and EV_CLEAR; delivery accumulates elapsed expirations and advances the deadline. High-resolution timers remain a separate one-shot path. Persistent user events are emitted once per wait batch and remain available to a later wait. APR events use their own filter. These semantics matter independently of queue lifetime.

AIO waits: batch state is part of the API

KernelAioWaitRequests() in src/libs/libKernel.cpp is registered under NID lgK+oIWkJyA. It accepts 1–128 request IDs and writes one state per ID. Mode 1 waits for all IDs to be terminal; mode 2 also permits an unnotified completed/aborted request to satisfy the wait. If all IDs are terminal, either mode returns. For one ID, the mode argument is ignored. An invalid ID is reported as KERNEL_ERROR_ESRCH in its state slot rather than necessarily failing the entire call.

usec == nullptr supplies no deadline; a non-null pointer supplies a microsecond budget, including an immediate check for a zero budget. Completion is checked before a timeout is returned, so an already completed request can succeed with zero time available. Success writes the remaining budget. Polls and waits share the atomic KERNEL_AIO_STATE_NOTIFIED bit, and a final notifying scan handles competition between waiters. Null ID/state pointers, invalid counts and invalid multi-ID modes return before modifying output states.

src/libs/libKernel.cpp — the single-request wrapper
int KYTY_SYSV_ABI KernelAioWaitRequest(int32_t id, int32_t* state, uint32_t* usec) {
    return KernelAioWaitRequests(&id, 1, state, KERNEL_AIO_WAIT_AND, usec);
}

The read/write submission functions currently perform their KernelPread/KernelPwrite work inline; an AIO-shaped API does not by itself imply a background I/O worker. The pragmatic pattern

A great many functions here validate arguments, log them, set a flag and return OK. That is not laziness. For a large fraction of console APIs the observable contract really is "accept this configuration and do not fail" — the game calls Init, checks for a non-negative return, and moves on. The engineering work is in knowing which functions need real behaviour, and that knowledge comes from watching games fail.

Error codes are not arbitrary

src/libs/errno.h is console error constants. Returning the right negative value matters: games branch on specific codes, and returning a generic failure where the game expected ERROR_NOT_FOUND can send it down a completely different path.

Worked example: implementing a missing function

A small, understood HLE contract can make a good first contribution. An unresolved import is a research lead, not proof that returning success will improve compatibility. Use the developer curriculum to turn a hypothesis into evidence.

Step 1 — find what is missing

Run the game with logging to a file and search for stub messages:

kyty_emulator.exe --game "D:\Games\Example" --redzone --printf-direction File --printf-output-file _kyty.txt

The loader logs every import it could not resolve, with the NID and the owning module. A line naming a function the game then calls is your target.

Step 2 — work out what it should do

Combine these sources; none alone proves the complete contract:

  1. Call-site evidence. Inspect registers, verified argument memory and how the caller uses results. One call does not reveal every argument, optional field or error path.
  2. Symbol and type evidence. A NID database can suggest a name, not prove a signature. Verify parameter count/types, signedness, structure size/offsets and the guest ABI from lawful reference material and code evidence.
  3. Behavioral evidence. Specify success, failure, output writes and side effects before coding. Preserve a failing regression case. A guessed value that advances one title is a hypothesis, not a verified implementation.

Step 3 — write it

Add to the appropriate module file — or create one following the template in chapter 22:

AGC and PM4: how work reaches the GPU

The game never calls a draw function Kyty can intercept. It writes packets into a buffer and hands the buffer to the kernel. Understanding that distinction is the key to the whole graphics stack.

What an AGC call actually does

On a PC, vkCmdDraw goes into a driver that eventually produces hardware commands. On the PS5 the game is the driver. AGC functions are thin builders that write dwords into memory the game owns:

uint32_t* KYTY_SYSV_ABI AgcCbDispatch(CommandBuffer* buf, uint32_t thread_group_x,
                                            uint32_t thread_group_y, uint32_t thread_group_z, ...);
uint32_t  KYTY_SYSV_ABI AgcCbDispatchGetSize();
uint32_t* KYTY_SYSV_ABI AgcCbSetShRegistersDirect(CommandBuffer* buf, ...);
uint32_t* KYTY_SYSV_ABI AgcCbReleaseMem(CommandBuffer* buf, uint8_t action, ...);

Note the …GetSize() companions. A game asks for a command’s size in bytes so it can lay out its buffer in advance, then calls the builder to fill its dwords. Keep the return type and size unit attached to each API. This is why Kyty's reimplementations must produce byte-identical output to the real driver: the game may compute offsets into the buffer, patch values later, or jump over regions.

src/libs/agc.cpp — byte size of an indirect shader-register command
uint64_t KYTY_SYSV_ABI AgcDcbSetShRegistersIndirectGetSize() {
    PRINT_NAME();
    return 5u * sizeof(uint32_t); // 20 bytes, five dwords
}

src/libs/libAgcDriver.cpp registers this function as LIB_FUNC("nNlUtdDDvZ0", Gen5::AgcDcbSetShRegistersIndirectGetSize). Its declaration in agc.h, the returned byte count and the paired command builder are one ABI contract.

Patch functions prove the point

The AGC API includes functions such as AgcSetCxRegIndirectPatchSetAddress, AgcJumpPatchSetTarget and AgcWriteDataPatchSetAddressOrOffset. These exist so a game can build a command buffer once and rewrite specific fields each frame. A reimplementation that produced structurally different packets would break them.

Two buffers, not one — the draw stream and the constant stream, which correspond to the two engines described in chapter 26.

The command processor

Kyty implements, in software, the front end of an AMD GPU: the unit that reads packets from memory and turns them into state changes and work.

Packet format

The stream is a sequence of 32-bit dwords. Each packet begins with a header whose top two bits give the type. Everything Kyty handles is type 3:

src/graphics/guest_gpu/pm4.h
#define KYTY_PM4(len, op, r)                                        \
    (0xC0000000u | (((static_cast<uint16_t>(len) - 2u) & 0x3fffu) << 16u) | \
     (((op) & 0xffu) << 8u) | (((r) & (Pm4::R_NUM - 1u)) << 2u))

#define KYTY_PM4_R(cmd_id)   (((cmd_id) >> 2u) & (Pm4::R_NUM - 1u))
#define KYTY_PM4_LEN(cmd_id) ((((cmd_id) >> 16u) & 0x3fffu) + 2u)

And the extraction, from the packet dumper:

const auto packet_type = static_cast<PacketType>(cmd_id >> 30u);
const bool sh_gx       = (cmd_id & 0x2u) == 0;
const uint8_t op       = ((cmd_id >> 8u) & 0xffu);

The colour bands map to the fields: type, count, opcode, then the Sony sub-selector. Note that the handlers assert on exact header values — CpOpDrawIndexAuto requires precisely 0xC0012D00 — so a malformed stream fails loudly rather than silently.

KYTY_CP_OP_PARSER(CpOpDrawIndexAuto) {

    EXIT_NOT_IMPLEMENTED(cmd_id != 0xc0012d00);       // exact encoding expected

    uint32_t index_count = buffer[0];
    uint32_t flags       = buffer[1];

That is the pattern throughout pm4Handlers.cpp: assert on what is not understood, unpack the fields, call into CommandProcessor, report the size.

Mechanisms a real command processor has

MechanismWhat it isWhy it matters
DE / CE counters Two engines walk the stream. The Constant Engine runs ahead prefetching constant data; the Drawing Engine follows. IT_INCREMENT_CE_COUNTER, IT_WAIT_ON_CE_COUNTER and IT_WAIT_ON_DE_COUNTER_DIFF keep them in step. Get this wrong and constants are stale by a frame or two — drifting, hard-to-localise corruption.
Constant RAM A 48 KB scratch area — uint32_t m_const_ram[0x3000] — that the CE writes and the DE dumps into memory. Heavily used for ring-buffered per-draw constants.
End-of-pipe events IT_RELEASE_MEM / IT_EVENT_WRITE_EOP: "when everything before this has completed, write this value there, and optionally raise an interrupt." How the game learns a frame is done. Kyty maps these onto Vulkan timeline semaphores and its own event queues.
Indirect buffers IT_INDIRECT_BUFFER is a call: jump into another buffer, then return. Pm4Execution keeps a stack of cursors. Engines split state into reusable chunks. Without this you see a fraction of the commands.
Predication IT_SET_PREDICATION makes subsequent packets conditional on a memory value. Occlusion-culled draws must actually be skipped. ShouldSkipPredicatedPackets() gates them.
Blocking waits IT_WAIT_REG_MEM spins until memory matches a condition. Kyty returns Pm4ProcessResult::Blocked and suspends the submission rather than busy-waiting, so a stalled graphics queue does not starve compute.

Why agcRegisterDefaults.inc is 215 KB

The largest file in the repository is a table of default register values. It exists because of how the real driver works: at context reset it writes a complete default state, and games then only set what they change. If Kyty's defaults differ anywhere, state leaks between draws in ways that are almost impossible to attribute — a blend mode set by one draw silently applying to the next.

Games can also ask for these defaults directly, which is why AgcGetRegisterDefaults2 is an exported function.

Register decoding versus draw validation

DecodeRenderControl() in pm4Handlers.cpp records DB_RENDER_CONTROL, including copy_depth_to_color and copy_stencil_to_color, without rejecting those bits immediately. A later state write can replace them before a draw uses them. RenderExecutor::ResolveRenderDepthTarget() in src/graphics/host_gpu/renderer/depthRenderTarget.cpp handles inactive or unbound attachments, then rejects unsupported depth-copy state for a draw with a bound attachment. Accepting a register write does not mean the corresponding rendering operation is implemented.

Sharps, user data, and shader resource tables

How a shader finds its textures. There is no analogue in any PC graphics API, and it is the reason the shader recompiler needs a dataflow analysis.

User data: the only channel into a shader

A shader stage receives up to 64 dwords in its first scalar registers, written by IT_SET_SH_REG packets. That is the entire parameter-passing mechanism. Inside those dwords a game may place, in any arrangement it chooses:

  • An inline descriptor — a V#, T# or S# sitting directly in registers.
  • A pointer to a table in memory containing descriptors, which the shader loads with s_load_dwordx4. Tables may point at further tables, to arbitrary depth. This is the shader resource table, or SRT.
  • Plain constants — a vertex offset, a flag, an index.

The problem this creates

Suppose a pixel shader samples a texture. In the machine code you will see something like:

s_load_dwordx4  s[8:11], s[0:1], 0x20      // load a pointer from user data + 0x20
s_load_dwordx8  s[12:19], s[8:9], 0x40     // load a T# from that table + 0x40
image_sample    v[0:3], v[4:5], s[12:19], s[20:23] dmask:0xf

To bind a Vulkan descriptor, Kyty must determine which texture s[12:19] will hold — and that requires evaluating the shader's own address arithmetic before the shader ever runs. Current code does this through three layers:

1 · Typed SSA valueskytyTranslateProgram creates typed values; RewriteToSsa and simplification expose where descriptor-address inputs came from.
↓
2 · TrackResourceskytyWalks those values and records descriptor-table reads. Constant offsets get flattened slots; genuinely dynamic reads stay explicit.
↓ at draw time, every draw
3 · MaterializeResourceskytyExecutes the recipe against the current user data and guest memory, producing a concrete ResourceSnapshot: this exact address, this format, this size.

Why fast clears matter so much

A "cleared" render target on real hardware may contain no pixel data at all — only a metadata surface saying "everything is this colour." If Kyty ignored that and read the pixels, it would get stale garbage. Tracking clear state is therefore not an optimisation but a correctness requirement.

The shader recompiler

Typed LDS and instruction coverage

The recompiler adds V_CMPX_NLE_F16 and native 64-bit LDS atomic OR. Shared-memory storage exposes compatible typed views instead of separate unrelated 32-bit and 64-bit stores; shader-info collection and SPIR-V emission carry the required capabilities. Read spirvEmitterMemory.cpp, spirvEmitterMemoryHelpers.cpp and the compute/CFG regression tests together.

At main commit d2413fc2 (7 October 2026), the recompiler lives under src/graphics/shader/recompiler/. It is organised as an explicit compiler pipeline: frontend/decode, frontend/cfg, frontend/translate, a typed value IR and its passes, then backend/spirv.

Why it is hard, restated precisely

  • The input has no structure. No types, no functions, no variables — 64-bit instruction words operating on 106 scalar and 256 vector registers.
  • Control flow is data. As chapter 7 showed, branching is EXEC-mask manipulation. SPIR-V demands declared merge and continue blocks.
  • Resources are opaque. As chapter 28 showed, finding which texture a shader uses requires evaluating its own address arithmetic.
  • Wave semantics differ. The shader assumes 32- or 64-lane waves and uses cross-lane instructions; host GPUs have their own subgroup sizes and support levels.
  • Failure is invisible. A miscompiled shader produces wrong pixels with no crash and no log line. This is why the tests are enormous.

The pipeline

Two functions orchestrate everything. TranslateProgram() runs for each new permutation, with resource-plan extraction only on the first program miss; CompileProgram() runs once per resource specialisation and emits SPIR-V. Both log the expensive phases with the shader hash. Failures EXIT — nothing takes a std::string* error. Merged ES/GS geometry stages are compiled as ShaderType::Mesh Vulkan mesh shaders via DecodeFusedProgram().

Operand widths and formatted buffer access

V_MIN3_U16 uses VOP3 opcode 0x353. ApplyNativeVop3B16TernarySelectors() selects the low or high half of each source and the destination; Integer16Ternary() widens those selected unsigned values, emits UMinTri32, then writes one 16-bit half while preserving the other. The same helper uses signed inputs and SMedTri32 for V_MED3_I16. Destination/source overlap and inactive EXEC lanes need tests, not just a correct minimum formula.

64-bit comparisons and EXEC

The frontend includes I64/U64 false/true comparisons and selected relational CMPX variants. EmitIntegerCompare() reads full-width register pairs and sign-extends signed 32-bit literals for I64 comparisons, including V_CMPX_EQ_I64. EmitCompareResult() masks the result with the incoming EXEC; CMPX replaces EXEC and its low/high halves without writing VCC. Ordinary comparisons write their mask destination. The compute test switch --integer64-compare-only exercises signed/unsigned edge values, literal extension and wave32/wave64 masks. Check the individual opcode table before claiming another comparison or modifier is supported.

Stage 2–3 — control flow

The CFG is built by splitting at branch targets, then computing dominators, post-dominators, back edges, natural loops and strongly connected components:

The dispatcher fallback

Failure is a supported outcome, not an error. When structure cannot be recovered the recompiler emits the whole shader as a dispatcher: one loop around a switch on a program-counter variable, each basic block a case. This handles control-flow shapes that structured emission cannot represent directly; supported instruction and resource semantics still determine correctness.

BuildGraph() selects the fallback for an irreducible graph. A later Structurize() failure also selects it after restoring the original unstructured graph. Kyty records the failure kind, block, graph counts, and reason in the log.

Native tessellation and stage metadata

ShaderVertexInputInfo::logical_stage selects Vertex, Mesh, Local, TessellationControl or TessellationEvaluation. PrepareTessellationPrograms() prepares three programs; Tessellation.cpp analyses LS/HS memory dataflow to derive strides and lowers cross-stage memory. spirvEmitterTessellation.cpp emits the Vulkan tessellation stages. Enable this path with --tessellation; patch draws are skipped by default.

Wave size is stage metadata, not a universal 64-lane constant: vertex and pixel stages carry their own widths and the NGG prologue respects guest wave32. Mesh stages retain their own workgroup limits. Recent opcode work includes FP64 arithmetic/conversions, DPP8, packed integer and half-float operations, partial SDWA destinations, image float-maximum atomics and buffer-cache policy bits. Host FP64 denormal limitations are logged.

Full-float BVH32/BVH64 intersections compile through BvhIntersect and spirvEmitterBvh.cpp. The helper reads guest nodes through BDA and executes triangle/box math in SPIR-V; normal compute dispatch preserves surrounding shader work. A16, D16 and incomplete NSA forms remain unsupported. C11 traces the supported encodings, node layouts and GPU fixtures; this is not a Vulkan ray-query backend or a claim of universal game support.

The pass order matters

RewriteToSsa() runs before constant propagation, identity removal, and dead-code elimination. EliminateReadLane() may trigger that cleanup sequence again. The Vulkan renderer

Blend mapping and readback lifetimes

PipelineStaticParameters is 116 bytes. Depth-bounds enable and range are dynamic state. Inactive blend fields are canonicalized, and identical color/alpha equations share a key. Logical-alpha handling belongs to ShaderPixelInputInfo::alpha_blend_source and the effective blend factors, with None, SourceAlpha, SourceAlphaOne and SourceAlphaZero variants. blendMapping.cpp classifies supported remaps; unsupported combinations disable blending with a warning. Sampler LOD bias is clamped to the host limit.

The 64 MiB download ring is the common readback path, not a hard transfer limit. Oversized transfers allocate a temporary download Buffer; the deferred completion operation owns it until GPU completion, then invalidates host caches and copies back. See BufferCache::DownloadBufferMemory() and CommandScheduler::DeferPriorityOperation().

The host side. Its central job is caching: turning "this guest address range, in this format, used this way" into "this Vulkan object" — and knowing when that answer stops being true.

Renderer ownership and transfers

RenderContext directly owns PageManager, BufferCache, TextureCache and the mapped-range set. Its fault, invalidation, map/unmap, BDA preparation and garbage-collection methods replaced the separate GPU-resource manager. The owning renderer serializes pipeline-cache use, including saving while the GPU is running; the cache is not independently thread-safe.

Buffer readback is batched through a 64 MiB download ring. Clean guest buffers can stream directly; GPU-written aliases still require synchronization before CPU use. Image dirty-region queries honor CPU ownership and image-local readback validity. Texture alias resolution shares canonical layouts across linear/tiled, 1D/2D, mip-tail and depth/stencil views. DCC/CMASK clears must become real pixels before an expanded alias or video-out consumer can use them.

Draw preparation reuses shader bindings and reads vertex semantics directly from metadata. Release-label work is batched without redundant submissions; indirect dispatch counts are read from GPU buffers. These changes reduce per-draw work while keeping ordering and resource lifetimes explicit.

Memory coherency

Sparse texture uploads

BufferCache::ObtainBufferForImage() reads streamed mip ranges through Memory::TryReadSparseBacking(). The guest address-space owner validates the complete range and rejects private mappings before the backing store copies resident pieces and zero-fills holes. A hole inside an owned sparse reservation is not the same as an arbitrary invalid guest address; do not replace failed reads with unconditional zeroes.

The single hardest problem in the project, and the source of the bugs that are hardest to reproduce. A console has unified memory; a PC does not.

The problem, stated plainly

On a PS5, CPU and GPU share one pool of physical memory. A game writes vertex data with the CPU, then draws with it. Shared backing avoids a mandatory copy between separate CPU and GPU allocations, but ordering and visibility still require the guest’s synchronization and cache-coherency rules.

On a PC, the GPU has its own memory. Kyty's Vulkan resources are copies of guest memory. So the emulator must answer two questions that the game never asks:

  • Has the CPU changed this data since I last copied it to the GPU? (→ upload)
  • Has the GPU changed this data since the CPU last read it? (→ download)

And it must answer them without any cooperation from the game.

The upload path

Before a draw reads a texture, the renderer asks which sub-ranges the CPU dirtied:

src/graphics/host_gpu/memoryTracker.h
template <typename RangeFunc, typename UploadFunc>
    void ForEachUploadRange(uint64_t vaddr, uint64_t size, bool is_written, RangeFunc&& range_func,
                            UploadFunc&& upload_func) {
        static_assert(std::is_nothrow_invocable_v<RangeFunc&, uint64_t, uint64_t>);
        static_assert(std::is_nothrow_invocable_v<UploadFunc&>);
        CheckNotInUploadCallback();
        Iterate<true>(vaddr, size, [](RegionManager*, uint64_t, uint64_t) {});
        const auto* previous_upload_owner = std::exchange(s_upload_owner, this);
        Iterate<false>(vaddr, size, [&](RegionManager* manager, uint64_t offset, uint64_t bytes) {
            manager->lock.lock();
            manager->ForEachModifiedRange<DirtySource::Cpu, true>(manager->GetCpuAddr() + offset,
                                                                  bytes, range_func);
            if (!is_written) {
                manager->lock.unlock();
            }
        });
        upload_func();
        if (is_written) {
            Iterate<false>(vaddr, size,
                           [](RegionManager* manager, uint64_t offset, uint64_t bytes) {
                               manager->template ChangeState<DirtySource::Gpu, true>(
                                   manager->GetCpuAddr() + offset, bytes);
                               manager->lock.unlock();
                           });
        }
        s_upload_owner = previous_upload_owner;
    }

Three things to notice:

  • Only dirty sub-ranges are copied. The transfer granularity depends on the buffer/image path, tracking pages and tiling; a changed tile does not guarantee a one-tile copy.
  • Locks are held across the callback. The user's range_func runs with region locks held, which is why it is required to be noexcept.
  • Protection is re-armed afterwards. Otherwise the next CPU write would go unnoticed.

The download path

Download iteration visits the requested GPU-dirty ranges under each region lock. The callback is required to be noexcept; clear controls whether GPU-dirty state is cleared:

template <bool clear, typename Func>
    void ForEachDownloadRange(uint64_t vaddr, uint64_t size, Func&& func) {
        static_assert(std::is_nothrow_invocable_v<Func&, uint64_t, uint64_t>);
        CheckNotInUploadCallback();
        Iterate<false>(vaddr, size, [&](RegionManager* manager, uint64_t offset, uint64_t bytes) {
            std::scoped_lock lock(manager->lock);
            const auto       address = manager->GetCpuAddr() + offset;
            manager->template ForEachModifiedRange<DirtySource::Gpu, false>(address, bytes, func);
            if constexpr (clear) {
                manager->template ChangeState<DirtySource::Gpu, false>(address, bytes);
            }
        });
    }

The invariants, enforced by hard failure

This code is unusually defensive, and the reason is worth internalising: a coherency bug produces corruption many frames later, with no traceable link to its cause. So Kyty converts each one into an immediate crash at the point of the mistake.

void CheckNotInUploadCallback() const noexcept {
    if (s_upload_owner == this) {
        EXIT("memory tracker re-entered from upload callback\n");
    }
}

And in InvalidateRegion, the state update runs twice — once to decide whether a flush is needed, once to verify the flush actually released every GPU-owned page:

template <typename Flush>
void InvalidateRegion(uint64_t vaddr, uint64_t size, Flush&& on_flush) {
    ...
    if (!update_cpu_state()) return;      // nothing GPU-owned; done
    std::forward<Flush>(on_flush)();      // flush GPU work
    if (update_cpu_state()) {
        EXIT("memory invalidation retained GPU-owned pages\n");
    }
}

How a CPU write is actually caught, end to end

  1. Resource tracking installs write watchers through PageManager, protecting guest pages whose CPU changes need tracking.
  2. The game later writes to the texture. Ordinary code — mov [rax], rbx.
  3. The CPU faults. The OS delivers it to KytyExceptionHandler (chapter 18).
  4. Memory::HandleGpuFault coordinates invalidation or readback as required, updates tracking and protection, and returns true.
  5. Execution resumes; the write completes. The game never knew.
  6. The next draw that reads the texture calls ForEachUploadRange, which reports exactly that page as dirty and copies it.

A game does not "present a frame." It registers buffers, renders into one, and asks the display hardware to scan it out at the next vertical blank. Reproducing that protocol faithfully matters more than it sounds.

Step by step:

  1. Register. The game hands over guest addresses plus a tiling and format description. Kyty records them; the texture cache creates images lazily.
  2. Render. Ordinary draws into one of those buffers, through the normal command stream.
  3. Flip. VideoOutSubmitFlip is queued, not immediate. A flip submitted while another is pending must block, exactly as on hardware — games rely on this for pacing.
  4. Notify. Flip and vertical-blank events are delivered into the game's event queues.

Virtual vertical blank

A timer fires at the configured rate — 60 Hz by default, --vblank-frequency — and pushes events into every queue that registered for them. This must stay steady even when rendering is slow, because many engines drive their entire simulation from it. A game that waits on vblank and gets it late does not just render late; it simulates late.

The final blit

Only at the very end does the guest's buffer reach the host window. The swapchain path is ordinary Vulkan: acquire an image, blit or resolve the guest buffer into it, present. swapchain.cpp handles format negotiation, present modes and resize.

APR command order and waits

A reading order for the source

Reading 123,000 lines front to back does not work. Read it as a sequence of complete journeys, each one small and each one ending somewhere satisfying.

1 · The whole boot, end to end2 hoursmain.cpp → emulator.cpp → RuntimeLinker::Execute(). Small files; you will finish knowing the shape of the entire program. Resist every temptation to follow a call into graphics or the loader. Chapters 11–12 are the map.
2 · One HLE function, all the way through2 hoursPick something small in src/libs/ — libAppContent.cpp is a good size. Find its LIB_FUNC, then follow RuntimeLinker::Resolve() to see how the guest's relocation reaches it. Chapters 15 and 22.
3 · The loader in detailhalf a dayLoadProgramToMemory, ParseProgramDynamicInfo, Relocate, PatchProgram. Run a game and read the log alongside — every segment address, size and protection is printed. Chapters 13–17.
4 · Follow one drawa dayTurn on --command-buffer-dump, run a 2D game, find an IT_DRAW_INDEX_AUTO. Then trace the six functions of chapter 31. This is the spine of the graphics stack.
5 · One shader, compileda day or twoTurn on --shader-log-direction File. Read the decoded listing, then the CFG, then the IR. Keep AMD's document 70648 open. Chapters 28 and 30.
6 · The coherency machineryhardestPageManager → MemoryTracker → TextureCache. Read tests/MemoryTrackerTests.cpp first — the tests state the invariants more clearly than the implementation. Chapter 32.

Habits worth adopting early

  • Run with logging on and read it. Kyty logs deliberately and enormously: every module load, every segment, every unresolved NID, every shader compile phase with timings. Most questions are answered faster by the log than by the source.
  • Treat EXIT_NOT_IMPLEMENTED as a map. Grep for it. Each of the ~980 sites marks a case the author knew about and chose not to handle.
  • Read the tests as specification. For the shader compiler and the memory tracker they are more precise than any comment.
  • Keep the boundary in mind. Guest pointer or host pointer? Guest thread, GPU thread, or main thread?

Glossary

Every term used in this book, defined. Filter to find one quickly.

ABIApplication binary interface — the machine-level contract: which registers carry arguments, who preserves what, how the stack is laid out. See System V and Microsoft x64.
AGCThe PS5's low-level graphics API, called Gen5 in this codebase. Its functions build PM4 packets rather than issuing draws.
AJMThe console's fixed-function audio decode block. Takes batched job records rather than function calls; Kyty routes each job to LibAtrac9 or FFmpeg.
AMPRThe PS5's asynchronous memory mapping and paging engine. Like the GPU, it consumes command records.
Back edgeA control-flow edge from a block back to one of its dominators — that is, a loop.
Basic blockA straight-line run of instructions with one entry and one exit. The unit a control-flow graph is built from.
CE / DEConstant Engine and Drawing Engine — two cooperating GPU command engines synchronised by counters, with the CE prefetching constants ahead of the DE.
CFGControl-flow graph. Basic blocks as nodes, branches as edges.
CMask / FMaskFast-clear mask and MSAA fragment mask — metadata surfaces beside a render target.
Command processorThe GPU front end that reads PM4 packets from memory and updates hardware registers. Kyty implements one in software.
DCCDelta Colour Compression. Metadata alongside a render target that compresses colour writes. Its address lives in the T# descriptor.
DescriptorA packed block of bits describing a resource. On RDNA 2 these live in registers or memory rather than in API-managed slots. See sharp.
Direct memoryPS5 physical memory, allocated by physical offset and mapped to a virtual address as a separate step.
Dispatcher fallbackThe recompiler's escape hatch for shaders whose control flow cannot be structured: one loop around a switch on a program-counter variable, each basic block a case.
DominatorBlock A dominates B if every path to B passes through A. Used to find loops and merge points.
EOPEnd of pipe. An event that fires when all preceding GPU work has completed, typically writing a value to memory and raising an interrupt.
ELFExecutable and Linkable Format, the Unix executable format. The PS5 uses it with custom type and tag values.
EXEC maskThe 64-bit register holding which lanes of a wave are currently active. Manipulating it is how RDNA 2 expresses branching — and why converting to SPIR-V is hard.
Fetch shaderA small generated shader that reads vertex attributes into registers before the real vertex shader runs. RDNA 2 has no fixed-function vertex input.
Flexible memoryPS5 paged memory from a fixed per-title budget declared in param.json.
FlipAsking the display to scan out a different buffer at the next vertical blank. The console's equivalent of "present."
Gen5This codebase's name for AGC, the PS5 graphics API.
GOTGlobal Offset Table — an array of pointers the dynamic linker fills in, so code can reference external symbols without being patched. Kyty writes its own function addresses here.
Guest / hostGuest = the emulated PS5 and its software. Host = the real PC, OS and GPU. Nearly every design decision in the project is about this boundary.
HLEHigh-level emulation. Reimplementing what a console's system libraries do, in native code, instead of running the originals.
HTileA compressed metadata surface accompanying a depth buffer, storing per-tile depth ranges for fast rejection and fast clears.
IrreducibleA control-flow graph containing a loop with more than one entry point. Cannot be expressed in structured form; triggers the dispatcher fallback.
JITJust-in-time compilation — translating guest instructions to host instructions at run time and caching the result. KytyPS5 contains none, because the instruction sets already match.
LaneOne invocation within a wave. 32 or 64 lanes execute the same instruction stream in lockstep.
LLELow-level emulation. Simulating the hardware and running the console's own firmware. Accurate, slow, and requires copyrighted system files.
Merge blockThe block where two branches of a conditional reconverge. SPIR-V requires it to be declared in advance; RDNA 2 has no such concept.
Microsoft x64Windows' calling convention: four integer arguments in rcx rdx r8 r9, plus 32 bytes of caller-reserved shadow space.
NIDThe 11-character encoded hash naming an exported symbol in place of a readable name. Written hash#library#module.
NGGNext Generation Geometry — RDNA's unified geometry pipeline, used by PS5 shader-stage combinations and primitive paths.
Page faultA CPU exception raised when memory is accessed in a way its page permissions forbid. In this project it is a primary control-flow mechanism, not just an error.
PLTProcedure Linkage Table — small stubs that route calls through the GOT so external functions need no code patching.
PM4AMD's GPU command packet format. A stream of 32-bit dwords; type-3 packets carry an opcode and a body length.
Post-dominatorBlock B post-dominates A if every path from A to the exit passes through B. Used to compute merge blocks.
PRTPartially Resident Texture — a sparse texture where only some tiles are backed by memory. Has its own tiling family.
ProsperoSony's internal codename for the PS5, and the namespace name used in Kyty's graphics code.
PRX / SPRXA PS5 shared library module. Games may ship their own alongside eboot.bin.
RDNA 2The GPU architecture the PS5's graphics core is based on. Its shader instruction set is the recompiler's input language.
Rect listA three-vertex primitive describing an axis-aligned rectangle. Used constantly for full-screen passes; has no Vulkan equivalent.
RelocationA record telling the loader to write a computed value at a given offset, because the final address was not known at compile time.
SELFSigned ELF. Sony's executable container: a small header and segment table wrapping an otherwise standard ELF64 file.
SGPR / VGPRScalar and vector general-purpose registers. Scalar values are uniform across the wave; vector values are per lane. Descriptors always live in SGPRs.
SharpAMD's term for a resource descriptor. V# buffer (4 dwords), T# image (8 dwords), S# sampler (4 dwords).
SPIR-VVulkan's binary shader intermediate language, and the recompiler's output. Requires structured control flow and declared types.
SRTShader Resource Table. A possibly-nested table of descriptors in memory, reached from a pointer in user data. Kyty must statically work out how to walk it.
StructurisationRecovering declared merge and continue blocks from unstructured control flow, so SPIR-V can express it.
SubgroupVulkan's name for a wave. Subgroup size and supported operations vary by host GPU, which is why Kyty has a portable fallback lane-mask mode.
System VThe System V AMD64 calling convention, used by the PS5, Linux and macOS: six integer arguments in rdi rsi rdx rcx r8 r9.
Tiling / swizzleThe non-linear memory layout GPUs use for images so that a 2D neighbourhood lands in one cache line.
Timeline semaphoreA Vulkan synchronisation object carrying a monotonically increasing counter, rather than a binary signalled state. Kyty's MasterSemaphore.
TLS / TCBThread-local storage and its thread control block. Reached on the PS5 through the fs segment, which is why the loader rewrites those instructions.
User dataUp to 64 dwords written into a shader's first scalar registers by SET_SH_REG packets — the only channel by which a draw passes parameters to its shaders.
VblankVertical blanking interval. Kyty generates a virtual one at a configurable rate; many engines pace their whole simulation off it.
WaveA group of 32 or 64 shader invocations executing one instruction stream in lockstep.

Performance: why this design is fast

Every design decision in this project is a performance decision in disguise. This page collects the ones that matter: why an HLE emulator can be fast at all, the five choices that make it fast, and an honest list of where the time actually goes.

Read

The headline — guest code runs natively — is one of five design choices, and it would not be enough on its own. The others are about not paying for the parts of a real console that don't matter.

Choice one — no interpreter

The guest CPU is the host CPU. Every guest instruction is one host instruction, so the emulator's per-instruction cost is effectively zero — it only spends time when the game calls into the OS or out to the GPU. That is the whole reason topic 02 exists. The cost of this choice is the ABI wall (topic C2): the game's System V registers and the host's Microsoft registers disagree, so every boundary crossing needs annotation or assembly.

Choice two — imports cost one jump

When a game calls a console function, the normal cost would be: trap into a kernel, switch context, dispatch. Here it is a push + jmp. The runtime linker rewrites the GOT slot once at load time (topic 07), and the JIT stubs in jit.h (topic C2) are just bytes: push <index>; jmp <handler>. After resolution, a console call is exactly as expensive as a local function call. No interpreter, no dispatch table, no syscall.

src/loader/jit.h — the whole import cost
// 68 00 00 00 00          push     <index>
// E9 E0 FF FF FF          jmp      <handler>

Choice three — GPU work is batched

The game doesn't make a Vulkan call per draw — it writes PM4 packets into a ring buffer, and the GPU thread (topic C4) consumes them in bulk. The CPU and GPU overlap: the game can run several frames ahead while the GPU thread chews on queued command buffers. The overlap is held together by timeline semaphores (topic C4, the Lab's timeline tool) so a submission waits on the previous tick instead of stalling the CPU. That is why a heavy frame doesn't necessarily cost the CPU anything.

Choice four — shaders are cached, not recompiled

The RDNA2 → SPIR-V translation is the most expensive per-object work in the emulator — a complex shader can take hundreds of milliseconds the first time. The answer is a cache keyed on the shader's chksum/hash: recompile once, reuse every frame after. shader.cpp even logs cache hits so you can see it working:

src/graphics/shader/shader.cpp — the cache-hit path
static void LogShaderProgramCacheHit(const char* stage, uint64_t shader_hash, uint64_t words) {
    static std::atomic<uint32_t> log_count {0};
    if (log_count.fetch_add(1, std::memory_order_relaxed) >= 512) { return; }
    LOGF("Shader cache hit: %s hash=0x%016" PRIx64 " (%" PRIu64 " words)\n",
         stage, shader_hash, words);
}

The Vulkan pipeline is cached too, so the driver doesn't re-compile SPIR-V either. The practical consequence: the first frame after a shader compiles is slow; everything after is free.

Choice five — coherency without copies

A real GPU shares memory with the CPU, and games rely on that. The naive host approach is to copy the game's buffers to the GPU on every use. Kyty's approach (topic 10) is to let the guest write, and fault on the GPU's behalf: the page manager watches guest pages, and when the GPU needs a buffer it uses, the coherency layer uploads the dirty pages on demand. The trick is the page-fault channel does the dirty tracking for free — no copies, no polling, no per-draw bookkeeping.

Where the time actually goes

Be honest about the costs, because they are the interesting performance facts:

And the honest framing for the whole project: HLE is fast because it skips the expensive parts, not because it is clever in the expensive parts. No firmware to boot, no silicon to simulate, no instruction interpretation. The parts that are translated (shaders) and the parts that are emulated (OS calls) are where the CPU time is spent, and each has been made one-time-cost or per-call-cheap. That is the whole performance model — and the answer to "why does the first frame hang then run fine" is always shaders.

Measuring, not guessing

Two switches exist for this. --profiler-direction Network streams into the Tracy profiler (the trace appears in the 3rdparty toolbox from topic C6), and the KYTY_PROFILER_FUNCTION scopes sprinkled through shader.cpp and the renderer light it up. If you ever need to answer "what is slow", that is the instrument.

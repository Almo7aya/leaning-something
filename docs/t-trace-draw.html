One draw: PM4 to GPU completion

Trace a selected non-indexed draw through state, shader programs, resource bindings, Vulkan recording and completion.

Read, trace, prove

Prerequisites: PM4, register state, shader translation and coherency. This source trace at 2650478 follows an ordinary, non-indexed triangle-list draw with a vertex shader, an active pixel shader and a color target. It is not a standalone three-word program or a captured frame.

Four different milestones

Accepting a guest submission, recording a Vulkan draw, completing that submission on the GPU, and displaying an image are different events. A “DrawComplete” CPU log records progress through the host draw function; it is not a GPU fence and does not prove that any pixels were displayed.

1. Identify the packet and the state it consumes

At CpOpDrawIndexAuto in src/graphics/guest_gpu/command_processor/pm4Handlers.cpp, the current parser accepts header 0xC0012D00, consumes two payload dwords and rejects flag bits outside 0x22. The first payload dword becomes the vertex count, despite the parser's local variable name index_count.

Illustrative packet, not a complete render workload:
header       count       flags
0xC0012D00   0x00000003  0x00000002

Header = 1 dword; payload = 2 dwords; total = 3 dwords = 12 bytes.
Count = 3 vertices; flag 0x02 is inside the accepted mask 0x22.

At this handler, buffer points to the payload, not the header. Its return value 2 is the number of payload dwords consumed. Confusing these coordinate systems shifts every subsequent packet.

The packet does not contain a full draw state. Earlier commands establish shader addresses, user-data registers/descriptors, targets, topology, offsets and instance count. Locate those writes in the same submission and preceding preserved state. Three vertices with no usable shader or targets need not reach a Vulkan draw.

2. Follow the guest-to-renderer handoffs

Guest-side command generation and state writes
  -> AgcDriverSubmitCommandBuffer (graphics queue)
  -> submit_dcb -> GuestGpu::Submit -> queued Submission
  -> GuestGpu::ThreadRun -> GuestGpu::Process
  -> CommandProcessor::Process -> CpOpDrawIndexAuto
  -> CommandProcessor::DrawIndexAuto
  -> RenderExecutor::DrawAuto
  -> PrepareDrawRenderState -> ExecutePreparedDraw
  -> recorded Vulkan draw
  -> BufferFlush / CommandScheduler::Submit
  -> timeline signal observed -> eligible deferred work
  -> presentation is a separate downstream path

The AGC submission route above is one route, not the only entry point. AgcDriverSubmitCommandBuffer chooses graphics versus compute based on its queue context; this trace assumes graphics. submit_dcb passes a span of guest commands. GuestGpu::Submit queues that span; a span is a borrowed view, not an owning copy. Follow the guest's submission/lifetime protocol before assuming it may overwrite the command storage.

The GPU worker processes submissions, retaining suspended execution state when a command stream blocks. GuestGpu::Process associates the command processor with a guest submit ID, initializes its buffer, drives constant/draw streams and flushes after progress. A guest submit ID is a debug/guest-processing identity; it is not the Vulkan scheduler's completion tick.

These are not independent immutable snapshots. RenderContext owns the caches, and resource preparation can read guest memory, read back metadata, submit work, wait and restart the scheduler. PrepareGraphicsBindings deliberately finalizes image identities before reserving draw buffers.

The critical command-buffer boundary

ExecutePreparedDraw fetches the current buffer.Handle() after resource preparation. From that point onward, the commit path must not introduce guest-memory accesses that can finish/restart the scheduler. Holding an earlier Vulkan handle across preparation can target an obsolete command buffer even when the C++ wrapper reference remains valid.

4. Distinguish three different cache questions

  • Program/resource analysis: the program cache retains analysis and resource-plan data, plus mutable scratch/snapshot storage borrowed by runtime stage data. Do not assume borrowed pointers own independent immutable results.
  • Shader permutation: a new permutation rebuilds temporary translated IR before compilation; a matching compiled permutation can be reused. “Same shader code” does not necessarily mean the same specialization.
  • Host graphics pipeline: the key combines stage identities with packed static state. At this snapshot PipelineStaticParameters is 126 bytes, includes logical-alpha source remapping, and excludes dynamic stencil state. A driver disk-cache hit does not by itself bypass the emulator's RDNA translation.

Record which layer hit or missed. Do not use a generic “cache hit” log as proof that resources were refreshed correctly or that the pipeline matches today's draw.

5. Commit bindings and record the draw

On the selected ordinary path, ExecutePreparedDraw commits vertex bindings and stage descriptors, applies dynamic graphics state, starts rendering, binds the graphics pipeline and calls EmitDrawPrimitives. For a non-indexed triangle list, that function records vk_buffer.draw(count, instance_count, first_vertex, first_instance). A local variable named index_count in the common draw description still supplies the vertex count here.

If shaders write buffers, the function ends rendering and records a shader-write barrier. Reaching its final log means these CPU-side recording steps ran; it does not mean the GPU has executed them. Indexed, mesh, tessellation, indirect and rectangle conversion paths add different preparation or emission steps. They are outside this selected trace.

6. Cross the submission and completion boundary

CommandScheduler::Submit ends the current command buffer. Under the graphics queue mutex, it obtains the next timeline tick, adds the master semaphore signal and submits the buffer and semaphore values to the Vulkan queue. It then invalidates the recorded Vulkan buffer handle. Flush submits and begins the next buffer; it is not a wait. FlushAndWait also waits for the returned tick before beginning the next buffer.

MasterSemaphore::Refresh obtains observed GPU progress; IsFree(tick) means KnownGpuTick() >= tick. PopPendingOperations checks completion and priority-operation ordering before running eligible deferred callbacks. Keeping a resource alive until the CPU call returns is insufficient if a submitted command still references it.

Illustrative timeline (not measured frame data)
CPU records draw using resource A for tick 6
CPU submits tick 6                 observed GPU tick remains 4
CPU moves to later work            A must remain alive
GPU completion reaches tick 6      A's tick-6 use is complete
Eligible deferred callback runs    retirement still follows owner/dependency rules

Completion of this submission alone does not prove presentation, guest CPU visibility of every GPU write, or absence of future uses of A. A readback also needs the correct copy, visibility and CPU-side completion path. Oversized downloads in this snapshot retain temporary backing until deferred completion; the ordinary ring's lifetime rules are not permission to free that backing early.

Work through Lab B to reproduce a wrong-retirement-tick bug without a GPU. It tests caller bookkeeping, not Vulkan synchronization itself.

Pass the draw gate

Checkpoint

Self-check: DrawComplete was logged, but completed tick is 4 and the draw used tick 6. May A be destroyed?

No. The log is CPU-side recording evidence. Tick 6 has not been observed complete. Even after it completes, check later uses and the owner's deferred-release rules; the log alone never grants permission.
